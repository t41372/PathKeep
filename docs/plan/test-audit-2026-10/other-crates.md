## A items (pin wrong behavior)

### A1. `windows_apply_and_remove_report_schtasks_failures`: vault-platform/src/scheduler.rs:1036

- **Asserts:** when `schtasks /Create` is denied, `ApplyResult.message == "schedule.windowsAccessDeniedInstallMessage"` (line 1075). The other branches of the same field carry English sentences.
- **Code pinned:** vault-platform/src/scheduler/windows.rs:272-279. `message` is an i18n key in one branch and prose in the others.
- **Evidence:** the UI never translates `message`. `src/features/backup/schedule-actions.ts:34` does `throw new Error(result.message)`, and `use-finish-setup.ts:118` does the same. `describeError` (`src/lib/errors.ts`) says it is "not responsible for localising". Only `scheduleCopy()` maps `schedule.*` keys, and it is used on `titleKey` / `detailKey` / `labelKey`. A denied Windows user sees "Couldn't install. schedule.windowsAccessDeniedInstallMessage", which breaks AGENTS.md principle 5 (i18n shipping contract). The translated copy exists at `src/lib/i18n/messages/backup-schedule.ts:236` and is never reached.
- **E2E:** none. E2E runs the scheduler sandbox on macOS, which is never "denied".
- **Action:** fix the code. Carry the denied state in `step_results[0].detail_key` (already `schedule.verifyWindowsRegisterAccessDenied`) and keep `message` as diagnostics, or translate `message` through `scheduleCopy` when it is a key. Then assert the typed field.

### A2. `takeout_jsonl_round_trips`: browser-history-fixtures/tests/takeout_roundtrip.rs:196

Also pinned by lines inside `classify_payload_path_covers_takeout_scope_matrix` (parser takeout/tests.rs:207-209) and `browser_history_payload_covers_jsonl_…` (takeout/tests.rs:500).

- **Asserts:** a `.jsonl` file goes through the production Takeout classifier and parser and comes back as URLs and visits.
- **Code pinned:** browser-history-parser/src/takeout/source.rs:67-75. The first branch of `classify_payload_path` returns `WillImport` for any file name ending in `.jsonl`, with `reason_code: "jsonl-history-fixture"`. It runs before the Chrome-scope, My Activity and outside-scope rules, so `Google Fotos/x.jsonl` is `WillImport` too. vault-core uses this classifier for real imports.
- **Evidence:**
  - docs/features/archive.md:183: only a dedicated Chrome history payload enters the importer.
  - archive.md:184: the parser must match the real Takeout envelope, "not just repo-made fixtures". The reason code itself calls this path a fixture.
  - archive.md:187: other Google product exports are `known-but-ignored`.
  - Consequence: `vault-core/src/takeout/import_flow.rs:194-207` fails the whole import when one `WillImport` file doesn't parse.
- **E2E:** none. Scenario: a Takeout zip with `Chrome/BrowserHistory.json` plus another product's `.jsonl` previews only the Chrome visits, lists the `.jsonl` as ignored, and imports exactly the fixture's visits.
- **Action:** fix the code. Route `.jsonl` through the normal scope rules, or keep JSONL only in the fixture harness. Then drop this test and the JSONL lines in the two parser tests.

### A3. `recover_interrupted_rekey_removes_a_corrupt_marker`: vault-convert-sqlcipher/src/legacy_recovery/rekey.rs:324

### A4. `recover_interrupted_import_removes_a_corrupt_marker`: vault-convert-sqlcipher/src/legacy_recovery/import.rs:342

- **Assert:** when the old app's rekey or import crash marker can't be parsed, recovery deletes it and reports nothing to recover.
- **Code pinned:** `read_rekey_journal` (rekey.rs:82-95) and `read_import_journal` (import.rs:94-107) delete the marker and return `None`. `recover_locked` (mod.rs:74-130) then sets `config.json` from the history-vault header alone and reports `Healed`.
- **Evidence:**
  - The module's own failure modes (legacy_recovery/mod.rs:6-7, written 2026-10-07, after the tests from 2026-06-30) include "clearing a marker it could not act on".
  - With a readable marker, rekey.rs:165-190 refuses to commit a Plaintext config while source-evidence is still Encrypted (rekey.rs:5-6 names this failure mode). With an unreadable marker, the same crash state is healed to Plaintext anyway.
  - For import, a cut commit with an unreadable marker ends up as a mixed archive. quality-matrix.md:79 (鐵律 3) requires "consistent-or-fail-closed（…或 marker 留著 fail-closed），永不 empty/mixed".
  - restore.rs:83-89 and 133-150 already keep an unreadable marker and fail closed.
  - The counter-argument is in the code: the doc comments on `read_rekey_journal` (rekey.rs:78-81) and `read_import_journal` say a corrupt marker is removed so that "a damaged marker can never block opens forever". That is an older, deliberate choice. The newer module header and 鐵律 3 argue for failing closed. This audit sides with failing closed because the same disk state is refused when the marker is readable, and the recovery screen gives the user a way forward, so the launch isn't blocked forever.
- **Confidence:** moderate. The trigger needs a damaged marker, which is rare. Both tests run on an empty folder, so a narrower fix (drop the marker only when both canonical headers agree) would still pass them.
- **E2E:** none (needs a crash state on disk); Rust is the right layer.
- **Action:** fix the code. Keep an unparseable marker and return `Unrecoverable` unless the history-vault and source-evidence headers agree, as restore.rs:139 does. Replace both tests with one that builds the drift state (Plaintext history-vault, Encrypted source-evidence, garbage marker) and asserts `Unrecoverable`, the marker kept and the config untouched.

## The most harmful B/C

1. **vault-worker post-backup warning helpers** (archive_flows.rs:1089-1149, :1706, :1760; 8 tests). They say failures "surface as warnings". In the product they never reach a screen. `run_backup_now` appends og:image, intelligence-refresh and AI auto-index warnings (archive_flows.rs:228-330) after `run_backup_with_progress` has written the run row. The run sheet reads warnings only from `runs.warnings_json` (vault-core archive/read_models.rs:145, write_runs.rs:128). `backup-runner.tsx:62-70` ignores `BackupReport.warnings`. So "intelligence refresh failed" is invisible, against archive.md:318 ("warning honesty 不能被藏起來"). The tests also pin untranslated English text and report routine successes ("removed 4 rows") as warnings. E2E scenario: a backup whose post-backup step fails shows a localized warning in Backup → run → Warnings.
2. **Windows scheduler on an English-stderr stub** (vault-platform scheduler.rs:935, :1085). The `cfg(any(test, coverage))` schtasks stub returns English stderr, and the classifier matches that text (windows.rs:639-647). schtasks.exe prints in the display language, so on zh-TW / zh-CN Windows a missing task likely reads as a permission warning. The tests can never show it. Verify on a localized host, then classify by exit code or the Task Scheduler API.
3. **Parser batch and capability snapshots** (browser-history-parser chromium/mod.rs:1246, firefox/mod.rs:625, safari/mod.rs:906). They pin exact chunk sequences (`[2,1,2,2,2,1]`) and about 25 capability counts. That data is written to `source_batches` and nothing reads it back. They came from a mutation-hardening commit.
4. **`all_ten_fields_keep_the_projection_weights`** (vault-search tests/contracts.rs:116). It pins the rank order produced by ten weights no doc specifies. lexical-recall-v2.md:152 only says title ranks above URL. `brute()` and ast.rs:85 copy the weights too, so a tune breaks four more tests.
5. **`manual_backup_refreshes_deterministic_insights_automatically`** (vault-worker tests.rs:1303). It pins internal job-type names (`visit-derive`, `daily-rollup`, `structural-rebuild`) and progress 100. The uncommitted incremental-aggregates work will break it while Insights stays correct, and insights.spec.ts already proves the user-visible numbers.
6. **`autocheckpoint_pragma_is_ignored_and_native_threshold_is_measured`** (vault-store src/checkpoint.rs:164). It pins Turso 0.8.1 internals that turso-migration-design.md:83 says the design doesn't rely on, so the next Turso upgrade can fail the gate.
7. **Tests that keep dead commands alive.** These cover `security_status` (no caller of `securityClient.getStatus`), `prefetch_og_images` (og-images.md:172), `get_browse_day_insights`, the queued-assistant path (`ask_ai_assistant` has no caller), `export_conversation_file`, and the Takeout `parse_history` / `stream_history` / `inspect_history` duplicates in the parser (12 tests; vault-core has its own copies).
8. **English heuristics tested with hand-written messages:** vault-worker `queue_failure_classifier_…` (tests.rs:239) and `backup_failure_classification_…` (scheduled.rs:160); src-tauri `classifies_biometric_markers_from_their_producing_sentences` (command_error.rs:296), which hand-copies 13 sentences instead of calling the producer. A reworded provider or OS message breaks the product, and the test still passes.
9. **Coverage omnibus walks:** src-tauri `dispatch_command_decodes_all_browser_mirror_command_payloads` (dispatch/tests.rs:611, ~700 lines, asserts nothing, runs in no gate), six `worker_bridge` "cover" tests (~1100 lines of `let _ = …_impl(…)`), and vault-worker `worker_support_helpers_cover_…` / `ai_worker_helpers_cover_…`. Every IPC signature change has to be carried through them.
10. **macOS apply/remove on the launchctl stub** (vault-platform scheduler.rs:1153, :1185, :1242, :1277). The real bootout/loaded guard (macos.rs:708-735) is compiled out of every unit test. `:1185` even asserts the stub's own `"stub bootstrap"` string. schedule.spec.ts and sandbox_tests.rs prove the real flow through the sandbox seam.

## Cross-cutting observations

- **Where the B/C come from:** mutation and coverage commits ("harden rust parser mutation contracts", "restore strict coverage gate", and the `cfg(coverage)` twins). The tell-tale names are `*_covers_*`, `*_cover_*` and `coverage_*`, plus comments like "exercise it so the coverage gate stays honest".
- **Stubs below the outermost endpoint.** The `cfg(any(test, coverage))` env-var stubs for launchctl and schtasks replace real decision logic, which quality-matrix 鐵律 4 forbids. The newer `SchedulerHost::Sandbox` seam is at the right level, and E2E already uses it.
- **Randomized torture seeded from the clock** (vault-crypto envelope_crash.rs:82, search_tamper.rs:238 via common/mod.rs:151-160) goes against 鐵律 3's "DETERMINISTIC". Keep them, but use a fixed default seed.
- **Write-only data pinned as contract:** parser capability snapshots, schema observations and warnings go to `source_batches` and are never read. `ScheduleStatus.warnings` is "diagnostic-only". Takeout `reasonCode` / `classification` / `detectedLocale` are never read by `src/`.
- **E2E duplicates (kept as D but safe to drop):** vault-worker `rekey_requires_the_current_password_…` (security.spec.ts), `delete_all_data_removes_the_installed_automatic_backup` (wipe.spec.ts), and the three migration.rs tests (move.spec.ts).
- **E2E gaps that leave Rust tests as the only guard:** Takeout and Safari import, legacy crash recovery, ranking order (title above URL), the Ask chat flow, model-download cancel, and post-backup warnings. Proposed scenarios are in the tables.
- **Outside test scope, noticed on the way:**
  - The Ask markdown renderer opens model-produced links through `open_external_url`, which accepts any `file://` URL (src/features/ask/markdown.tsx:37, vault-platform launcher.rs:68). That belongs in ai-security-posture.md.
  - `useRepairLegacySchedule` treats a no-op repair as an error, while Remove treats the same no-op as done (schedule-actions.ts:34-42).
  - og:image background fetching is on by default with no onboarding disclosure (og-images.md "仍未處理").
