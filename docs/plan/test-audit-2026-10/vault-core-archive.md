# vault-core unit-test audit: archive, takeout, chrome, stars, annotations, maintenance, durable_io, fault_inject

Scope: every `#[test]` in `src-tauri/crates/vault-core/src/` under `archive/` (343), `takeout/` (64), `chrome/` (29), `stars/` (43), `annotations/` (23), `maintenance/` (15), `durable_io.rs` (25) and `fault_inject.rs` (11). That is 553 tests. A plain grep finds 555, but two `#[test]` matches in `fault_inject.rs` are inside comments. All paths below are relative to `src-tauri/crates/vault-core/src/` unless they start with `docs/` or another crate.

Method: read-only. For each test I read the test, the code under test and the doc section that governs it, and looked up the adding commit for the A/B/C items and clusters. Nothing was compiled or run. Commits that added large numbers of coverage tests, and so give a strong C prior: `2423e66d test(qa): restore strict coverage gate`, `d17a9442 refactor(rust): modularize runtime and harden archive flows`, `fe8f9cef`, `aacb455d`, `f0766795 test(import): pin minor ingest contracts`, `1d831127`, `4fd3d20b`, `3b7c14f7`.

Categories: **A** pins wrong behavior · **B** pins incidental detail · **C** mutation/coverage leftover · **D** keep.

Accepted-doc boundary: `docs/plan/program/quality-matrix.md` (2026-06-30 data-integrity rules) requires durable atomic writes, config/disk consistency checks, kill-at-checkpoint crash tests that assert the injected error text, and test seams only at the outermost I/O endpoint. Tests that implement those rules are D even when they assert error strings or call order. That is why `durable_io.rs`, `fault_inject.rs`, `write_lock.rs`, `maintenance/` and `wipe/` are mostly D. It reflects the doc, not a shortcut.

## Findings outside the four categories (read these first)

1. **23 og:image tests never run.** 17 in `og_images_fetch.rs`, 5 in `og_images_synth.rs` and 1 in `net_guard.rs` are `#[ignore]` ("requires a network socket"; most since b5ae1704, 2026-10-06), and no gate, CI workflow, `.modal-offload.toml` or package script passes `--ignored`. Among them are the only tests of the per-redirect-hop SSRF guard (`og_images_fetch.rs:1525`, `:1551`), the og:image sub-resource SSRF test (`:921`) and the DNS half of the URL guard (`net_guard.rs:159`). mockito binds 127.0.0.1 and needs no internet, so the D tests among them can run in the gate.
2. **A shipped DoS fix is gone from HEAD, and an ignored test hid it.** `cafac470` / `014db312` streamed the Bilibili API body with a running 64 KiB cap (`docs/plan/CHANGELOG.md:1932-1936` records it as shipped). Merge `a232bf76` dropped it and `02d36dd3` did not restore it. `og_images_synth.rs:82-87` again calls `response.bytes()` and only then checks the size, while the comment above still says it caps before parsing. `read_with_cap` no longer exists anywhere in the tree. `resolve_image_url_via_api_returns_none_when_body_exceeds_cap` (`og_images_synth.rs:418`) passes either way and is ignored.
3. **The og:image fetcher follows redirects with no per-hop SSRF check.** `build_fetch_client` (`og_images_fetch.rs:139-149`) uses `Policy::limited(8)`, and the comment at `:157-158` says "the og:image client is deliberately untouched". `docs/architecture/ai-security-posture.md:239` and `:245-250` say every redirect hop is guarded and that this "applies to both fetchers". og:image fetching is on by default in Background mode. BACKLOG.md:650 lists the gap. No test pins it either way.
4. **The content-fetch hop guard is compiled out in tests.** `enrichment/content_fetch.rs:77-86` makes `redirect_hop_is_blocked` always return `false` under `cfg(any(test, coverage))`. That conflicts with quality-matrix rule 4 (production checks stay in the measured build, and only the outermost endpoint is a seam). The file is outside this audit's scope.
5. **Day insights is a dead command kept alive by its tests.** `get_browse_day_insights` has no caller in `src/` or `tests/` since the v0.4 redesign (`src/lib/backend-client/explorer.ts:123` is defined and never called). Its 15 tests, and a `#[cfg(coverage)]` second copy of a production function (`archive/history/day_insights.rs:403-442`), keep it compiled. Delete the command, the module and the tests together.
6. **Spec not implemented, no test either way.** `docs/features/archive.md:77,89` require row versioning for URL titles. Canonical `urls` overwrites `title` in place (`archive/ingest/writes.rs:139-142`).
7. **Stale docs the tests follow (do not "fix" these tests against them).** `docs/architecture/lexical-recall-v2.md:119,158-159` still describe a 200/400 fuzzy window that `search.md:11` and `recall.md:91` removed. `docs/features/annotations.md:108` still says the Starred view caps at 2000, against `data-model.md:337-340`. `docs/features/og-images.md:29,103-105,172` give an old UA, timeout and redirect count, and say coverage stats have no callers.

## A items

### A1. A `.jsonl` file is imported as Google Takeout browser history (4 tests)

- Tests: `recognize_and_parse_takeout_payloads` (takeout/tests.rs:724), `takeout_parsers_cover_blank_lines_arrays_and_unusable_payloads` (takeout/tests.rs:918), `inspect_takeout_collects_preview_rows` (takeout/tests.rs:102), `import_takeout_quarantines_unknown_files_and_skips_index_entries` (takeout/tests.rs:952).
- What they assert: `entries.jsonl` is recognized as an importable kind (724). A file of `{"url","title","visitedAt"}` lines previews and imports as visits (102, 918, 952). A top-level array that uses the My Activity field names `titleUrl` / `pageTitle` is accepted as `browser-json` records (918).
- Code under test: in `browser-history-parser/src/takeout/source.rs:67-75`, any file name ending in `.jsonl` returns `disposition: WillImport` with `reason_code: "jsonl-history-fixture"`. The product classifier itself names it a test fixture. `browser-history-parser/src/takeout/browser_history.rs:324-342` accepts `titleUrl` / `visitedAt` / `pageTitle` as fallbacks.
- Contradicting doc: `docs/features/archive.md:183` "目前 shipping scope 採 Chrome-first：只有 dedicated Chrome history payload（例如 `BrowserHistory.json`、`History.json`、德文化的 `Verlauf.json`）進入 importer。" and `:184` "parser 也必須對齊真實 Takeout envelope，而不是只靠 repo 自造 fixture". Google Takeout does not write browser history as JSONL. As it stands, any `*.jsonl` in a user's Takeout folder or zip is imported as visits if its lines carry a URL and a time.
- Counter-evidence I checked: the 2026-05 plan doc `docs/plan/program/import-test-harness-spec.md:20,229` lists "Takeout JSON / JSONL" as fixture formats to generate. And PathKeep's own JSONL export writes the same `url` / `title` / `visitedAt` fields, so this path happens to re-import a PathKeep export into a profile named "Imported browser history". No feature doc describes either use. If the owner wants JSONL import, it needs its own doc and label. It should not be a hidden branch of the Takeout classifier.
- Why it blocks a fix: removing the branch breaks these 4 tests directly. About 15 more tests use the JSONL helper only as their vehicle: the `write_takeout_fixture*` helpers in takeout/tests.rs, `Fixture::import` in takeout/batch_search_tests.rs, and `seed_takeout_fixture` in archive/tests.rs. Those are D in subject and only need their fixture changed. The real-shape helper `write_takeout_browser_json_fixture` already exists.
- Action: fix the code. Drop the `.jsonl` WillImport branch, or send it to needs-review like any other unknown history-like file. Move the helpers to the real `{"Browser History":[...{"time_usec":...}]}` shape and delete the JSONL-specific assertions. Test 952's name also says "quarantines" while it asserts the file is not quarantined (inverted in 329c5713 without a rename).

### A2. Chrome's microsecond `visit_duration` is stored in `visit_duration_ms` (1 test)

- Test: `e12_chromium_visit_duration_value_is_preserved_verbatim` (archive/ingest/dedup_scenarios_edge_cases/minor_data_integrity.rs:115), added in `f0766795 test(import): pin minor ingest contracts`.
- What it asserts: a Chromium `visits.visit_duration` of 6,543,210 (the fixture field is `visit_duration_micros`) lands unchanged in archive `visits.visit_duration_ms`.
- Code under test: `browser-history-parser/src/chromium/mod.rs:708` (`visit_duration_ms: row.get(7)?`, no conversion) and `archive/ingest/writes.rs:276`.
- Why it is wrong: readers treat the value as milliseconds. `intelligence/phase_three.rs:396-399` maps it to `foreground_duration_ms`, and `archive/history/timeline.rs:219` returns it to the frontend as `durationMs`. That inflates every duration 1000×, which `docs/plan/BACKLOG.md:647` already records ("Chromium `visit_duration`（µs）以 `_ms` 命名 verbatim 存（E12 accepted），但 `phase_three.rs` 把它當真 ms 聚合 → 1000× 膨脹"). The `_ms` suffix means milliseconds across the canonical schema (ADR-002:22 sets that rule for event times). The import-dedup audit (`docs/plan/program/import-dedup-audit.md:472`) says outright that this test "pins current value-preservation semantics", so it froze whatever the code did.
- Why it blocks a fix: converting at parse time, or renaming the column to `_us`, fails this test, and the BACKLOG item cites it as the reason the behavior is "accepted".
- Action: fix the code. Convert to milliseconds in the Chromium parser, or rename the column and evidence key and convert at the readers. BACKLOG.md:654 asks for a trade-off note first, per AGENTS.md principle 7. Then assert 6,543 ms for a 6,543,210 µs source.

### A3. A visit whose parent URL is missing is skipped, and a later visit moves the cursor past it (2 tests)

- Tests: `chunk_consumer_skips_visits_when_url_batch_has_not_populated_the_map` (archive/ingest/core_tests.rs:254, added in 76f4c528 "test(import): pin parser ordering skip contract"), and in part `chunk_consumer_persists_batches_and_reports_duplicate_progress` (archive/ingest/core_tests.rs:159, 2423e66d), which feeds one orphan visit (line 179) and expects it to be skipped (lines 209 and 221).
- What they assert: the visit is not stored, the batch succeeds, and the only trace is `skipped_records = 1`. The doc comment calls this "intentionally silent skip, not fail-fast".
- Code under test: `archive/ingest/consumer.rs:355-358` (`let Some(..) = resolve_url(..) else { p.skipped_visits += 1; continue; }`). Any later visit in the same batch then advances `w.last_visit_id` (`consumer.rs:394-395`), so the next incremental backup never reads the skipped visit again.
- Contradicting docs: `docs/features/archive.md:76` (the archive is append-only, records are never deleted). `docs/plan/program/import-dedup-audit.md:410-411`: "**No visit is silently dropped**: parser emits visit before URL → must be caught". `docs/plan/BACKLOG.md:647` lists orphan-visit drops as a bug ("需 warn 或 LEFT JOIN"). The adding commit's own message names the risk ("a batching refactor could silently drop visits"), and the test then pins that drop.
- Caveat: when the source really has no URL row for the visit, the visit cannot be stored with a URL anyway. In that case the fix may be a coded warning rather than a failed batch, and only the "silent" part of these tests has to change. For the ordering bug the test simulates, the visit is lost for good.
- Action: fix the code. Either fail the batch before the cursor moves, or store the visit with its URL and record a coded `BackupWarning`. Keep the duplicate and progress-counter half of :159.

## Other notes from reading the code under test (unverified unless stated)

- **og:image re-download loop.** With the "Up to 100/500 MB" link-preview setting at its cap, cleanup evicts never-shown images first (`archive/history/og_images.rs:310`). After a backup, cleanup runs before prefetch (`vault-worker/src/archive_flows.rs:293-327`), so prefetch picks the same newest pages again and downloads the same images on every backup. `cleanup_lru_evicts_least_recently_shown_first` pins the never-shown-first order. No doc defines it.
- **og:image AVIF.** The image `Accept` header advertises `image/avif` (`og_images_fetch.rs:72`), but `supported_image_mime` (`:629-638`) rejects it. A CDN that serves AVIF gets the page marked `unsupported_mime` and left alone for 60 days.
- **SERP rows churn.** Search-result pages get `MISSING`, which is retried every 30 days (`og_images_fetch.rs:262`). So every SERP row comes back into the refetch sweep. The test (`:860`) is a regression test for a real bug and stays D.
- **http→https image upgrade has no test.** `http_only_image_url_is_upgraded_to_https_by_production_pipeline` (`og_images_fetch.rs:939`) tests a 3-line helper, and every pipeline test passes `upgrade_image_url = false`.
- **NAT64.** `net_guard.rs:66-75` does not treat `64:ff9b::/96` as non-public (not checked against a spec).
- **Linux Firefox profile names.** `chrome/discovery.rs:295` reads `profiles.ini` from the parent of the profiles root. On Linux the file is inside the root, so profiles show folder names.
- **First-run E2E would not catch the Firefox-forks regression.** `tests/e2e/first-run.spec.ts:41-42` has an out-of-date comment and unchecks any profile it doesn't expect. `chrome/tests.rs:90` is the only guard.
- **HTML export has no charset.** See `every_format_writes_the_same_bytes_as_the_joined_export` above. No doc requires `<meta charset="utf-8">`, so it is B, not A.
- **Firefox transition codes.** See `e14_...` above: Day insights reads raw Firefox `visit_type` as Chrome transition codes.
