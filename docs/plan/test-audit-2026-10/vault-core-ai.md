# Unit test audit: vault-core AI, AI queue, agent store

Scope: every `#[test]` / `#[tokio::test]` in `src-tauri/crates/vault-core/src/ai/` (including
`tests.rs`, `tests_native/`, `code_mode/tests.rs`, `agent_tools/tests.rs` and the in-file test
modules), `ai_queue/tests.rs` and `agent_store/tests/`. Paths below are relative to
`src-tauri/crates/vault-core/src/` unless they start with `docs/`, `src/` or `vault-worker/`.

Method: read-only. Each test was read together with the code it calls and checked against
`docs/features/intelligence.md`, `docs/architecture/ai-security-posture.md` and
`docs/plan/program/quality-matrix.md`. Nothing was compiled or run. Every A item was re-read by hand
against the code before it went in.

(`embedding_external.rs:899`) is `#[cfg(coverage)]` and is never compiled by `cargo test`.

## A items (pins wrong behavior)

### A1. The rebuild time estimate is computed for the removed candle engine (3 tests)

Tests:

- `reembed_constants_match_s1_benchmark`, `ai/working_set.rs:323`
- `reembed_estimate_math_uses_constants_and_gpu_speedup`, `ai/working_set.rs:331`
- `estimate_reembed_full_counts_unique_pages_and_sizes_cost`, `ai/tests_native/working_set.rs:171`

What they assert: `CANDLE_CPU_DOCS_PER_SEC == 1.25` and `METAL_SPEEDUP == 10.0` ("so a silent edit
(which would mis-state the user-facing cost) is caught"), that 9,000 pages take exactly 120 CPU minutes,
and that 3 pages take `3 / 1.25 / 60` minutes.

Code: `reembed_estimate_for` (`ai/working_set.rs:219`) always divides by the candle Qwen3 rate
(`ai/working_set.rs:166`, "Measured single-text candle throughput").

Why it is wrong:

- The rebuild runs on the built-in static model, not candle. `docs/features/intelligence.md:362`:
  "介面上沒有分開設定 embedding provider，本機語意搜尋用內建的靜態模型".
  `src/features/ai-setup/use-semantic-index.ts:106` fixes the provider to
  `BUILT_IN_STATIC_EMBEDDING_PROVIDER_ID`; the candle download command "was removed in 2026-10 because
  no frontend called it" (`vault-worker/src/intelligence/model_download.rs:14-15`).
- The static tier was chosen for ~8,000 docs/s (`docs/plan/program/ai-redesign-2026/01-research-findings-2026.md:82`),
  about 6,400 times the 1.25 docs/s used here.
- Users see it: Settings → AI → Rebuild search index (`src/features/settings/ai-section.tsx:133-153`)
  renders `estMinutesCpu` into "This indexes {count} pages again and takes about {minutes} on this
  computer" (`src/lib/i18n/messages/settings-ai.ts:111`). For 100,000 pages the dialog promises about
  1,333 minutes (22 hours) for a job that takes seconds to minutes.
- History: the estimator came with the candle/Metal tier (2026-06-22); the 2026-10 Settings
  rewrite wired it to the static-tier dialog.

Blocks the fix: any estimate based on the engine that will actually run fails all three tests.
(A config hand-edited to select the candle engine would still get the right number from 1.25 docs/s;
an estimate taken from the selected engine covers both cases, so the "6,400 times" applies to the
built-in static engine the UI sets up.)
E2E: none. Action: **fix the code** (estimate from the selected engine's measured rate), delete all
three tests, add S-REBUILD.

### A2. A reopened chat loses each citation's browser profile (1 test, one assertion)

Test: `load_conversation_reconstructs_citations_and_usage_for_the_answering_turn`,
`agent_store/tests/journal.rs:386`, assertion at `:452-454`:
`assert!(assistant.citations[0].profile_id.is_empty())`, commented "profile_id is not journaled".

Why it is wrong: `docs/features/intelligence.md:104`: "citation contract 至少包含 `historyId`、`profileId`、
URL / title、visited time、score". `agent_citations` has no profile column
(`store_schema/agent.rs:61-70`) and `agent_store/transcript.rs:269` rebuilds every citation with
`profile_id: String::new()`. The live stream carries the profile, so the same answer has a profile
while streaming and none after reopening.

Impact today: low; the Ask UI does not show the profile. The rest of the test (citations and usage land
on the answering turn, ordered, canonical URL kept) is a real data-integrity check.
E2E: partial, `upgrade.spec.ts` checks the migrated answer text only. Action: **fix the code** (journal
`profile_id` with each citation), flip line 454, keep the rest; later cover with Ask-answer.

### A3. The connection-test report says OpenAI / LM Studio / Ollama cannot call tools (1 test)

Test: `capabilities_reflect_request_format`, `ai/llm.rs:924`. Asserts `tool_call == false` and
`structured_output == false` for the OpenAI-compatible formats ("floor must not optimistically claim
tool calling").

Why it is wrong: the code no longer works that way. `request_format_self_certifies_tools`
(`ai/llm.rs:131-141`) returns `true` for every format, `probe_tool_capability` (`ai/llm.rs:159-166`)
returns `Ok(true)` without a network call, and the worker sends tools to LM Studio on that answer
(`vault-worker/src/intelligence/chat.rs:486-503`). The same `AiProviderConnectionTestReport` then
contradicts itself: `supports_tool_use = true` (`ai/read_model.rs:367-396`) next to
`llm_capabilities.tool_call = false` copied from `rig_llm_capabilities` (`ai/provider.rs:245-258`).
`docs/features/intelligence.md:358` makes the capability report part of the connection-test contract.

Impact today: low; `llmCapabilities` is typed in `src/lib/types/intelligence.ts:340-369` but nothing
renders it. E2E: none (E-CONN). Action: **fix the code** (one source of truth for tool support),
delete the floor assertions.

### A4. A script with no `return` yields `"null"`, so run_code's "no value" sentinel never fires (1 test)

Test: `a_void_program_yields_an_empty_output`, `ai/code_mode/tests.rs:1160`. Asserts
`outcome.model_text == "null"` for `const x = 1;`.

Why it is wrong: `code_outcome_to_tool_outcome` documents that "When the script returned nothing (no
`return`, or only whitespace) the empty text is normalized to an honest sentinel"
(`ai/agent_tools.rs:510-513`, sentinel at `:537`). The guest maps `undefined` to `null`
(`ai/code_mode_guest/harness.js:117`), so the text is `"null"`, never empty, and the model gets
`null` instead of "[run_code completed but returned no value]". It cannot tell "returned nothing" from
`return null`. The companion test `an_empty_no_error_outcome_is_normalized_to_an_honest_sentinel`
(`ai/agent_tools/tests.rs:537`, B) hides this by feeding `model_text: ""` for `let x = 1;`, an output the
real sandbox never produces.

Impact: model-facing only, low. Blocks the fix: making a void script reach the sentinel fails this test.
E2E: none (Ask-long). Action: **fix the code** (have the guest report "no value" distinctly), then
assert the sentinel through the real sandbox and delete the hand-built-input test.

## Findings that cut across files

### Tests of a fake: production I/O compiled out with `cfg`

`docs/plan/program/quality-matrix.md:80` forbids compiling production I/O out of the tested build. In
this area the real paths are replaced by `#[cfg(any(test, coverage))]` stubs (82 such `cfg` lines across `ai.rs`, `embedding_candle.rs`, `embedding_external.rs`, `embedding_static.rs`, `llm.rs`,
`provider.rs`):

- chat and streaming chat: `ai/llm.rs:530-645` real vs `:659-765` stub (canned text such as
  "lmstudio answer to '…' with 1 tool(s)");
- `run_llm_agent`, `embed_query`: `ai/provider.rs:478-537`, `:655-725` real vs `:543-566`, `:728-773` stub;
- external `/v1/embeddings`: `ai/embedding_external.rs:318-357` real vs `:366-430` stub;
- the candle forward pass, loader, selector and HTTP fetch (`ai/embedding_candle.rs:40-44` says so: "so
  the 100% coverage gate is met");
- the static and candle engine selectors (`embedding_candle.rs:216` real vs `:252` test,
  `embedding_static.rs:175-201`); the test selectors skip the "model on disk and verified" check.

The stubs behave differently from the product, and tests then pin the stub behavior: the external stub
makes vectors depend on query vs document role, the shipped provider ignores role
(`embedding_external.rs:322` `_role` vs `:421`), and `embed_returns_role_aware_normalized_vectors`
(`embedding_external.rs:774`) asserts the stub-only behavior. Every indexing test in `tests_native/`
embeds through these stubs; the pipeline under them (Vault, `.pkvec`, `.pkmap`, cursors) is real, so most
of those stay D.

Test switches also live in production code: stub behavior is selected by substrings of the provider
config id (`probe-roundtrip`, `network-error`, `tools-rejection`, `chat-error`, `stream-error`,
`stream-open-error` in `ai/llm.rs:176-179, 661-731`; `llm-error`, `batch-error`, `batch-short`,
`single-error` in `ai/provider.rs`; `embed-http-error` in `ai/embedding_external.rs:372-377`).
