# 上一頁 / 下一頁與 Windows、Linux 的視窗按鈕 — Trade-off

> **狀態：Accepted — 用戶 2026-10-12 選定 D（上一頁 / 下一頁放導航列；Windows、Linux 的視窗按鈕畫在底層右上角）**
> **範圍：** 導航列頂端、主面板的上邊距、Windows 與 Linux 的視窗外框
> **牽涉的已接受文檔：** [screens-and-nav.md](screens-and-nav.md) §導航（「沒有上一頁 / 下一頁按鈕」與導航列頂端、拖動區那段）

## 1. 為什麼要改

- 用戶要全域的上一頁 / 下一頁（2026-10-12）。現在只有洞察的 drill-in 有「← 洞察」，其他地方回不去，只能再點一次導航列。
- 視窗是兩層：底層是視窗背景，導航列與 macOS 的紅綠燈在上面；主面板是浮在上面的圓角面板。Windows 與 Linux 卻是系統標題列加上這兩層，看起來像別的 app 套了我們的內容，導航列頂端放的品牌標誌也只在那兩個平台出現。

## 2. 選項

**A. 上一頁 / 下一頁放主面板左上角（Finder / Safari）。** 主面板左上角是各畫面自己的東西（History 的搜尋列、Ask 與 Settings 的側欄），每個畫面都要讓位。

**B. 整個視窗頂端加一條 top bar，放上一頁 / 下一頁、搜尋與視窗按鈕。** 用戶看過後放棄：History 的搜尋搬到 bar 上不對勁，多一條 bar 也破壞兩層的設計。

**C. 只有快捷鍵與選單。** 看不到也想不到。

**D. 上一頁 / 下一頁放導航列；Windows、Linux 的視窗按鈕畫在底層右上角（用戶選的）。**

```
macOS                                    Windows / Linux
● ● ●                                                                  ─  ☐  ✕
 ‹ ›   ┌ 主面板 ──────────────────┐       ‹ ›   ┌ 主面板 ──────────────────┐
 🏠    │                           │       🏠    │                           │
 🕘    │                           │       🕘    │                           │
```

- **上一頁 / 下一頁**：導航列頂端、五個主畫面上面，兩個並排的小箭頭（macOS 在紅綠燈下面）。沒有上一頁時變灰。走 router 的歷史：篩選與選取用 `replace`，不進歷史，所以只會在畫面與 drill-in 之間跳。快捷鍵 ⌘[ / ⌘]（Windows、Linux 用 Alt+← / Alt+→）與滑鼠側鍵，在文字框裡不攔。
- **Windows、Linux 的外框**：不用系統標題列（`decorations: false`）。主面板的上邊距加大，露出一條底層，最小化 / 最大化（還原）/ 關閉畫在這條的右上角，跟 macOS 紅綠燈在左上角是同一個位置關係。這條空白處可以拖動，雙擊最大化 / 還原。導航列頂端的品牌標誌拿掉，三個平台的導航列一樣。
- **Windows 11 的貼齊版面（snap layouts）**：滑鼠停在最大化上要出現。用微軟的 `windows` crate 在 Rust 裡回應 `WM_NCHITTEST`，讓系統把那個按鈕當成最大化按鈕，不另加依賴。無邊框視窗的邊緣縮放、Aero Snap 拖到螢幕邊緣也要照舊能用。
- **macOS** 不變，只在紅綠燈下面多了上一頁 / 下一頁。

## 3. 怎麼比

- **一致**：D 讓三個平台都是同樣的兩層，按鈕在每個畫面同一個位置，不用每個畫面各自讓位；A 每個新畫面都要記得讓位。
- **空間**：Windows 上少一條系統標題列（約 30 px），主面板上邊距多出的那條比它窄，內容反而多。
- **風險**：自己畫的視窗按鈕要做到跟系統一樣好：最大化與還原的圖示切換、深淺色、關閉 hover 的紅色、鍵盤與輔助技術、snap layouts。做不到就比系統的差，所以這些都要在 Windows 實機確認，不能只看截圖。Linux 各桌面環境的按鈕不一樣，我們畫的是同一套，跟 macOS 紅綠燈一樣是 app 自己的樣子。

## 4. 決定

用戶選 D（2026-10-12）。`screens-and-nav.md` §導航改成：導航列頂端有上一頁 / 下一頁；Windows、Linux 不用系統標題列，視窗按鈕在底層右上角。

## 5. 落地（2026-10-13）

上一頁 / 下一頁、快捷鍵、滑鼠側鍵、導航列拿掉品牌標誌、Windows 與 Linux 關掉系統標題列並自己畫視窗按鈕：都做了（`screens-and-nav.md` §導航）。在 Windows 與 Linux 實機上都還沒看過（這台 Mac 編不了 Windows 版：`ring`、`aws-lc-sys` 要 mingw）。Windows 11 的貼齊版面還沒做：要在 Rust 裡回應 `WM_NCHITTEST`，而 WebView2 的子視窗蓋住整個內容區，這個訊息可能根本到不了頂層視窗，必須在 Windows 上試，另列 BACKLOG `WORK-WINDOWS-SNAP-LAYOUTS`。

**2026-11-14 補正（`WORK-WINDOW-FRAME-EVERY-SCREEN`）。** 10-13 的落地只做到一半：

- 按鈕畫在主畫面的版面（`AppFrame`）裡，而 `AppFrame` 只在存檔打開之後掛上。新手引導、App Lock、存檔密碼、啟動中、啟動失敗、復原、舊格式升級、存檔更新、整窗的錯誤畫面，在 Windows、Linux 上都沒有視窗按鈕。第一次打開 PathKeep 的人，從頭到尾都在新手引導裡。
- 拖動區（`drag-region.ts`）仍以為 Windows、Linux 有系統標題列，一個都沒標。上面那些畫面完全拖不動；主畫面按鈕旁那條也不能拖，雙擊不會最大化，與上面 §2 寫的不符。
- 主畫面開著對話框時，對話框的遮罩蓋住按鈕；模態對話框還讓頁面其餘部分不收點擊。

七月就犯過同一個錯：2026-07-02 把 macOS 的拖動條從主畫面的外框移到 app 的根，好涵蓋新手引導、鎖定、復原、錯誤畫面；2026-10-04 改用 shadcn 重做前端時又拿掉了。

修正之後：

- 這是視窗的事，不是哪個畫面的事。按鈕在 app 的根畫一次（`src/app/window-chrome/`），每個畫面都有。它在所有錯誤邊界之外，照結構，畫面渲染失敗時也在；這一點沒有實際看過錯誤畫面。它疊在所有遮罩之上，對話框開著時照樣能按，按了不會關掉對話框，也不搶走輸入框的焦點。對話框開著時，鍵盤與輔助技術碰不到它，與頁面其餘部分一樣；系統的快捷鍵（Alt+F4 等）照常有效。
- 有面板的畫面（主畫面、新手引導）照同一條規則在面板上方留出 32 px 的底層。
- 拖動分兩種。視窗底層（面板外圍、按鈕旁那條、鎖定／啟動／錯誤畫面的背景）三個平台都能拖，雙擊最大化。面板裡面（每個捲動畫面頂端 28 px、頁首與側欄的空白）只有 macOS 能拖：那裡的面板頂端落在紅綠燈那條標題區裡；Windows、Linux 的面板從那條 32 px 下面開始，面板裡面就是內容。

E2E 以前在瀏覽器頁面裡跑，那裡不是桌面視窗，沒有一個平台的外框出現過：沒有按鈕，沒有紅綠燈讓位，也沒有拖動標記。現在 dev bridge 的頁面可以代表某個平台的桌面視窗（`windowFrame`），`first-run-window.spec.ts` 與 `window-frame.spec.ts` 在最小視窗尺寸下逐一檢查新手引導、啟動中、啟動失敗、主畫面、指令面板與 App Lock。按鈕與拖動對真視窗做了什麼，在 Linux 的真視窗上用真的滑鼠點過，有三種環境：X11 的 xfwm4、GNOME 46 的 X11、GNOME 46 的 Wayland。新手引導、主畫面、App Lock 的三顆按鈕，從那條拖動，雙擊最大化與還原，指令面板開著時按最小化，關閉讓 app 結束，都有效（`artifacts/investigations/2026-11-14-window-frame/`）。

Linux 的這部分現在每次 CI 都跑：`first-run-native-window.spec.ts` 用 xdotool 操作 E2E 本來就開著的真視窗，視窗管理員是 mutter。它排在最前面，壞了會最先看到。
