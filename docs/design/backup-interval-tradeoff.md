# 自動備份的間隔：照定案文檔，或照 v0.4 — Trade-off

> **狀態：Accepted — 用戶 2026-10-10 選定 B（照 v0.4，改文檔）**
> **範圍：** onboarding 的備份頻率、Backup → 自動備份卡、新安裝的 config 預設
> **牽涉的已接受文檔：** [archive.md](../features/archive.md) 排程一節（已照 B 改寫）

## 1. 落差

`archive.md` 寫的是：預設每 12 小時；`6h / 12h / 24h / 72h` 是快捷，不是唯一選項；自訂是整數分鐘，最短 1 分鐘，沒有上限。

2026-10 redesign 做的是：

- Backup → 自動備份卡：每小時 / 每 6 小時 / 每天 / 自訂 / 關。自訂以分鐘、小時或天輸入，1 分鐘到 30 天（後端 `preview_schedule` 也只收這個範圍）。
- onboarding 預先選好每小時；選「手動」就不裝排程。
- 新安裝的 config 預設 72 小時。onboarding 選「手動」時留著它，所以之後在 Backup 打開自動備份時，畫面上沒有任何一個快捷是選中的。

沒有 trade-off 文檔，也沒經用戶同意。

## 2. 選項

**A. 照 `archive.md`。** 預設 12 小時，快捷 6 / 12 / 24 / 72 小時，自訂沒有上限。

**B. 照 v0.4，改文檔。** 保留每小時 / 6 小時 / 每天 / 自訂（1 分鐘到 30 天），onboarding 預選每小時；新安裝的 config 預設也改成每小時，跟 onboarding 一致。

**C. 混合。** 保留 v0.4 的快捷與上限，預設 12 小時（在快捷裡顯示成自訂）。

## 3. 怎麼比

- 每次備份是先複製瀏覽器的資料庫、再追加新的造訪，新的造訪少時很快。每小時備份讓「瀏覽器自己刪掉歷史之前」的空窗最短，`archive.md` 的保存目的也是這個。
- 12 小時不在 v0.4 的快捷裡；選 A 或 C 就要改快捷，或讓預設看起來像自訂。
- 30 天的上限：比 30 天更久才備份一次，瀏覽器可能已經把那段歷史清掉了（Chrome 預設保留 90 天，有些設定與清理工具更短）；排程的健康檢查也以這個間隔判斷逾期。

## 4. 決定

用戶選 B。`archive.md` 改成 v0.4 的做法；`AppConfig::default` 的 `due_after_hours` 從 72 改成 1。已經存著 72 小時的 config 不動：那是使用者當時的值。
