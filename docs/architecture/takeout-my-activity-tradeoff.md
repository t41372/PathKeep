# 匯入 Google Takeout 的「我的活動 → Chrome」 — Trade-off

> **狀態：用戶 2026-10-09 決定匯入 JSON（HTML 只認出來、請改選 JSON）。本文推翻 `archive.md`「Google Takeout 導入」的 Chrome-first（只讀 Chrome 產品的 `History.json`，「我的活動」標 `needs-review` 不匯入）。跨來源重複（§3.3）量過了，用戶選 C（都保存，只算一次）。**
> **範圍：** `browser-history-parser` 的 Takeout 辨識與解析、`vault-core/src/takeout/`、匯入卡的文案、`archive.md`。

## 1. 為什麼

Takeout 有兩份 Chrome 的瀏覽紀錄：

- **Chrome 產品**的 `Chrome/History.json`（舊稱 `BrowserHistory.json`）：Chrome 同步到帳號的歷史，觀察到只回溯約一年。PathKeep 現在只讀這份。
- **我的活動 → Chrome**：跟著帳號的「網路和應用程式活動」保留（3 / 18 / 36 個月自動刪除，或一直保留），可能比上一份久得多；只有開了同步並勾「包含 Chrome 記錄和其他網站活動」才有。格式可選 JSON 或 HTML，HTML 是預設。

用戶的樣本就是後者：一個 `我的活動/Chrome/我的活動.json`，109,644 筆，涵蓋一年（只看結構，見下）。不匯入的話，用戶拿到的唯一一份 Takeout 就整份被略過。v0.3 的 parser 曾讀 `titleUrl`，但時間只認 Chrome 產品的欄位、不認 `time`，也不解 Google 的轉址，所以那時匯入的結果要另查（§3.4）。

## 2. 格式（用戶的樣本，2026-10-09，只看欄位與格式）

一個 JSON 陣列，每筆：

| 欄位               | 內容                                                                                         |
| ------------------ | -------------------------------------------------------------------------------------------- |
| `header`           | 網站的網域，或 `Chrome`                                                                      |
| `title`            | `Visited <頁面標題>`；沒有網址的是 `Used Chrome`（238 筆）。中文帳號的匯出前綴仍是英文       |
| `titleUrl`         | 造訪的網址；109,406 筆有。87,139 筆包在 `https://www.google.com/url?q=<網址>&usg=…` 的轉址裡 |
| `time`             | UTC 的 RFC 3339（`…T…Z`，多數帶毫秒）                                                        |
| `products`         | `["Chrome"]`                                                                                 |
| `activityControls` | 例如「網路和應用程式活動」的名稱；部分有                                                     |

沒有造訪 id、轉場類型、開啟它的頁面（opener）、停留時間。

## 3. 做法

### 3.1 辨識

- 依內容辨識，不靠檔名：頂層是陣列，筆都有 `time`、`products` 含 `Chrome`、多數有 `titleUrl`，就是「我的活動 → Chrome」的 JSON。檔名只當快路（各語言的「我的活動」資料夾名不必列舉）。
- HTML（`我的活動.html` / `MyActivity.html`）照現在：認出來、不讀，匯入卡寫明請在 Takeout 改選 JSON。
- 同一份匯出裡同時有 Chrome 產品的 `History.json` 與「我的活動」：兩份都匯入（各自一個來源），重複的處理見 §3.3。

### 3.2 每一筆

- 網址：`titleUrl`；是 `google.com/url?q=` 的轉址就取 `q` 參數解碼後的網址（只解這一層 Google 轉址，其他網址原樣）。沒有網址的（`Used Chrome`）不是造訪，不寫入，記在解析警告裡（`no-page`）；別的 Google 產品的紀錄同樣（`other-product`）。
- 時間：`time` 解析成 UTC 毫秒（ADR-002）。
- 標題：去掉開頭固定的 `Visited `；其他語言的前綴見到再加（樣本只有英文）。去不掉就原樣存，不猜。
- 來源：獨立的 source profile `takeout::my-activity`（介面上是「Google Takeout · 我的活動」），跟 Chrome 歷史在同一個匯入批次、可一起復原。重匯不重複：`source_visit_id` 由網址、時刻、以及同一網址同一時刻的第幾筆組成，不含在檔案中的位置，所以之後再匯出一份（前面多了新的紀錄）也不會重複（`my_activity.rs`）。
- 沒有的欄位留空：opener 存成「沒記錄」（`from_visit` NULL，跟 Safari、Chrome 產品的 Takeout 一樣，洞察的「怎麼來到這裡」說無法知道）。

### 3.3 跨來源重複

「我的活動」記的多半是本機 Chrome 也記了的同一次造訪；Chrome 產品的 `History.json` 也是。之前每個來源各自存、各自去重，洞察把所有來源加起來，同一次造訪算兩、三次。

2026-10-09 在用戶真實資料的副本上量（本機建置、只輸出數字）：

- 樣本解析出 109,406 次造訪（另有 238 筆「Used Chrome」不是造訪）。其中 109,367 筆在舊版匯入的 Takeout 來源裡有同一個網址、同一個時刻（差 0 ms）的造訪；剩下 39 筆別的來源 1 秒內沒有同一個網址（2026-10-10 匯入副本時數出；當初的量測只印到小數一位，寫成了「全部」）。
- 跟本機瀏覽器比：只有 13.7% 的造訪落在本機瀏覽器也有紀錄的日子（本機 Chrome 從 2026-04 才有），其中同網址、1 秒內的有 5,166 筆（4.7%）；放寬到 60 秒、600 秒只多幾十筆，差值的 p90 是 0。重複就是同一個時刻。
- 已經算兩次的：本機 Chrome（Default）與舊版匯入的 Takeout 兩邊都有的造訪約 12,400 筆，Safari 6 筆；其他設定檔沒有。

用戶決定 C：都保存，同一次造訪只算一次。做法見 [same-visit-across-sources.md](same-visit-across-sources.md)。

### 3.4 用戶已匯入過的那份

舊版的匯入已經把 Google 的轉址解開、去掉了 `Visited ` 前綴：舊版匯入的 Takeout 來源裡，網址以 `https://www.google.com/url?` 開頭的造訪只有 197 筆（本機 Chrome 也有 127 筆，是真的造訪過那個轉址頁），標題以 `Visited ` 開頭的 0 筆；「我的活動」除了 39 筆，都在那裡找得到解開後的同一個網址。不需要升級時修正舊資料；重匯「我的活動」時，109,406 筆都寫進「我的活動」來源，其中 109,367 筆連到已有的那一筆、不再多算（§3.3）。

那 39 筆（2026-10-10，副本上只數）：17 筆的網址別的來源沒有；15 筆別的來源有，但差一小時以上；7 筆差 1 秒到 1 分鐘。9 筆在 1 秒內有一次造訪 Google 轉址頁（`google.com/url?…`）的紀錄：那次是經過 Google 的轉址點進去的，瀏覽器記下轉址頁、稍後再記下目的頁，「我的活動」在轉址的時刻記目的頁。所以「我的活動」的那一筆和瀏覽器的目的頁差幾秒，連不上，最多 7 次造訪會算兩次。不為這個放寬規則：要用「目的是這個網址的轉址頁」去配，每筆查找都要多做，換來的是 37 萬次裡的幾次。

### 3.5 證明

- `takeout-import.spec`：Takeout 資料夾放一份照樣本結構造的「我的活動」JSON（含轉址、`Used Chrome`、中文資料夾名），驗預覽的筆數、匯入後搜尋找得到解開後的網址與去掉前綴的標題、重匯不重複；HTML 仍只提示改選 JSON。
- 跨來源重複定案後，再加一個 E2E：本機 Chrome 已有的造訪，匯入「我的活動」後洞察不重算。
