# Archive compatibility: which PathKeep may open which archive

An archive outlives the build that wrote it. A user updates, goes back to an older build, restores a backup made by another version, or opens the same folder from two installed copies. This document is the rule for what a build does with an archive it did not write.

The short form: before a build creates, repairs, deletes or unlocks anything in a data folder, it reads `config.json` and decides whether the archive is one it may use. If not, it leaves the folder exactly as it found it and says why.

## Why this exists

v0.4.0 and v0.5.0 have no such check. Each acts on an archive before reading its config: it finishes an interrupted "delete all data", replays an install journal, creates folders, and only then finds out what it is looking at. The one thing they refuse is a database schema number they do not know, and their restore and move-import skip even that. v0.6 adds databases those builds do not know about; a v0.5.0 that changed encryption on such an archive would re-encrypt the files it knows and leave the rest under a key that no longer exists.

Those two releases cannot be changed. What v0.6 can do is make sure they stop early (the stamp below is a value they cannot parse, and they read the config before starting any service), and make sure no later build is ever in their position.

## The stamp

An archive has one format revision. It is written in `config.json`, in `archiveMode`:

```json
"archiveMode": {
  "formatVersion": 2,
  "mode": "Encrypted",
  "compatibility": { "revision": 1, "minReader": 1, "minWriter": 1 }
}
```

- `revision` is the archive's format.
- `minReader` is the lowest build level that can read it.
- `minWriter` is the lowest build level that can change it without damaging it.
- All three are positive integers with `minReader <= minWriter <= revision`. Anything else is a damaged control, not a version this build is too old for.

v0.4.0 and v0.5.0 write `"archiveMode": "Plaintext"` or `"Encrypted"`. That bare value is revision 0 and has no floors. Each database keeps its own schema version in its own migration table; the stamp does not repeat them.

Every build has one compiled level, `PRODUCT_ROOT_LEVEL` in `vault-core/src/admission.rs`. Nothing at run time changes it.

**This build is level 1 and writes revision 1.** Every archive it creates is stamped from the start, an archive of PathKeep 0.4 or 0.5 is brought up to revision 1 the first time this build opens it (below), and every archive a restore, an import or a conversion installs gets a stamp. From then on 0.4 and 0.5 stop at its config. The level went from 0 to 1 in the same change that made the build create everything revision 1 requires, the two agent-history stores: a build that claimed level 1 before that would have admitted archives it could not serve.

## The decision

With level `L` and a valid stamp:

| Condition       | Result                                                         |
| --------------- | -------------------------------------------------------------- |
| `L < minReader` | Refused: `archive-reader-too-old`                              |
| `L < minWriter` | Refused: `archive-writer-too-old`. There is no read-only mode. |
| otherwise       | Admitted, even when `revision > L`                             |

A higher revision with floors this build meets is the newer build's statement that this one is still safe. This build then uses its own layout and writes the `compatibility` object back **byte for byte** on every save, including keys it does not know. It never lowers a floor or replaces the revision with its own.

There are two outcomes, open or refuse. A read-only mode was considered and left out: the floors are in the format, so a later build can add one without a format change.

Reasons, as stable strings in errors and on the worker's stderr:

| Code                            | Meaning                                                                                                                                                                     |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `archive-reader-too-old`        | A newer PathKeep can read this archive; this one cannot.                                                                                                                    |
| `archive-writer-too-old`        | A newer PathKeep can change this archive safely; this one cannot.                                                                                                           |
| `archive-config-format-too-new` | `archiveMode` has a `formatVersion` above 2.                                                                                                                                |
| `archive-control-missing`       | There is an archive here and no `config.json`.                                                                                                                              |
| `archive-control-unreadable`    | `config.json` exists and cannot be read.                                                                                                                                    |
| `archive-control-invalid`       | `config.json` is not something any PathKeep wrote.                                                                                                                          |
| `archive-compatibility-invalid` | The stamp's numbers are not positive integers in order.                                                                                                                     |
| `archive-store-missing`         | The archive is stamped, a store its format requires is gone, and nothing says it is being created; or a released archive lacks one of its own stores when it is brought up. |
| `archive-uninitialized`         | Not a refusal: a worker command was asked to use an archive that was never set up.                                                                                          |
| `move-file-too-new`             | A move file only a newer PathKeep reads: its format is above the newest this build writes, or its archive's schema is above this build's. Found at the check.               |

The first three mean the archive is intact and needs a newer build. The next five mean its control is damaged or gone, or a store is. These are different messages to the user and are never reported as a wrong password, a corrupt database or an empty archive.

The desktop hands each of these to the window as the error's code (`src-tauri/src/command_error.rs`, which takes the refusal codes from `Reason::ALL`); when a cause chain holds several codes, the first one names the failure, the rest are its causes. The import dialog says the four that mean a newer PathKeep (`move-file-too-new` and the first three) as "made by a newer version of PathKeep, update it", and the archive password screen says "wrong password" only for `archive-password-wrong`, showing any other failure to open as one, with its reason.

## Bringing a released archive up to revision 1

An archive PathKeep 0.4 or 0.5 wrote has no stamp and five stores. Revision 1 adds two: the agent-history evidence (`archive/agent-history.db`) and its read model (`derived/agent-history-read-model.db`); their search index is a folder made when it is first needed. The first time this build opens such an archive it brings it up (`vault-core/src/maintenance/creation.rs`), in this order:

1. The stores revision 1 adds that are not there are made in a new folder under `staging/` (`creating-*`), with the archive's keys, closed with everything in their main files, and flushed. Nothing in the archive has changed yet. A folder with none of the five released stores is a new archive (setup writes the control before the first open) and gets all seven.
2. A record names those stores, what each holds once made, and that folder, and keeps the stamped `config.json` the next step writes. It is written where the install journal goes and under the journal's name (`archive/.pk-install-v2.json`, identity `pathkeep-create`), which 0.5 does not know.
3. `config.json` gets the stamp. From here 0.4 and 0.5 stop at the config.
4. Each store is moved into its place by one rename, only where nothing is, and only if it still holds what it held when it was made.
5. The folder is removed, then the record.

A crash at any of these points is finished by the next open, and nothing already in the archive is deleted or written over on the way:

- **Before the stamp, the record is only discarded, with its folder.** Nothing stopped 0.5 from opening the folder since, and 0.5 creates a store it lacks and saves into it; whatever it made stays. The next open makes what is missing then.
- **After the stamp, the stores the folder holds are moved in, only where nothing is**, and the open makes again any the folder lost. A store already in its place stays as it is. A store the folder no longer holds whole (a copy of the data folder cut short) is not moved in: moved in, it would be the store the archive opens, with no record left that could make it again. It is made again too.
- **No folder a store leaves outlives its record.** A folder stores were moved out of may still hold a second name of a store in place (below); removed later as a leftover nothing names (by the next bring-up, or by "Free up space", which clears `staging/`), it would free that store's data. A folder made again for lost stores is recorded before anything leaves it, and each folder is removed while the record still names it, before the record goes. One cut short while it is being made, before it is recorded, stays in `staging/` with empty stores that never went into place, and "Free up space" clears it.
- **A power cut that takes the control during the stamp is finished.** On FAT32 and exFAT the rename that writes the stamp over `config.json` can leave none. Without a control the folder would read as an archive that lost it, and be refused. The record keeps the stamped control: a folder without one, holding this record whose folder still holds every store it names as made, is an interrupted bring-up (`admission::census`), and recovery writes the control from the record, then goes on. Those stores are what bind the record to this folder; a record whose folder does not hold them, and a record whose control is not one this build stamps, write nothing.
- **A crash while a store is made leaves a half-written file under `staging/` only**, which goes with the record. The archive receives a store only whole.
- **A store's `-wal` or `-shm` in place without its main file stops the open** (`archive-store-missing`). A new main file beside it would be read with another file's log.
- **A missing required store is damage** (`archive-store-missing`). Only the creation record authorizes making a missing store. Required database writers open existing files at the filesystem boundary, so a file lost between preflight and writer startup also stays missing. Loss of a browsing or assistant store blocks the archive. Loss of either conversation store in an already stamped archive closes the conversation group. For a partial encrypted open, the control must declare encryption, the envelope must be a regular file that parses, and the supplied data key must open every browsing store. A remembered key can therefore open browsing directly. Password unlock also authenticates the envelope tag. After interrupted first setup it can use the exact pending envelope it authenticated and finish promoting that envelope. A retry after the file is put back needs no new stamp or journal.
- **A record that names anything other than a store this build knows, or any folder but one of its own under `staging/`, is refused** (`archive-control-invalid`), and it touches nothing.
- **A record carried into another archive's folder changes nothing there.** That archive's stores are in their places, and nothing is moved over a file.
- **Only "not found" is missing.** A store PathKeep cannot look at (a folder without permission) stops the bring-up before the record. An earlier version took such an error for a missing store, made the store again and stamped the archive, and the Ask conversations and Insights then opened empty.
- **A released archive missing one of its own stores is refused, not refilled** (`archive-store-missing`). The bring-up makes only what revision 1 adds. Making a lost store empty and stamping the archive would pass the loss off as part of the upgrade, and the Ask conversations or Insights would open empty with nothing said. Nothing is made or stamped; 0.5 can still open the folder.
- **A store under two names is not deleted under one of them.** On a file system without a journal (exFAT, FAT32), a power cut during the move of a store into its place can leave it in its place and in the folder it was made in, both names pointing at the same data. Removing the folder would free that data while the store in place still uses it, and the next file written there would overwrite the archive. A store the record moves in whose place holds the same bytes goes into the quarantine (`quarantine/creating-*/`), which the storage screen counts and the user frees, instead of with the folder. Nothing else of the folder ever left it, so nothing else is compared (its lock file has the same bytes as the archive's).

Once the archive is up, an open writes nothing: no record, the same control bytes.

### What an installed archive is stamped with

A restore, an import or a conversion replaces the archive with another one. The archive it installs keeps the stamp of the one it replaces, or takes the incoming archive's stamp when that is at least as high on all three numbers; an older snapshot or file never lowers it (`admission::compose`). When neither stamp is at least as high as the other on all three numbers, the operation is refused (`archive-compatibility-conflict`) before anything is installed. A folder without a stamp counts as this build's own, revision 1.

The installed archive's layout follows from that stamp.

**A restore brings back browsing data, under the archive's own encryption and password** (the user's decisions, 2026-11-15):

- **The agent conversations stay where they are**, never rolled back, converted or moved: they are only ever added to, and the tools delete their own transcripts (Claude Code after 30 days by default), so a rollback could only lose them and put back what was archived or thrown away since. The conversations in a copy are for a separate repair of damaged agent-history stores (BACKLOG `WORK-AH-REPAIR-FROM-COPY`), never for a restore. An archive that has none (one of 0.5's layout) gets empty stores.
- **The archive keeps its encryption mode, key and password.** Restoring a copy from before encryption was turned on must not turn it off and write everything, conversations included, unencrypted; nor may a restore put back a password changed since. The copy's stores are written under the archive's key: as they are when the copy is under the same key (a password change rewraps the same key, so keys are compared, not key files), rewritten table by table as in a mode change when it is not (a mode change since). An encrypted copy restored into an archive whose encryption was turned off is written unencrypted, as the user chose. The archive's key file stays; the copy's never replaces it.
- **This computer's settings stay**: App Lock and whether the keychain remembers the key, as an import keeps them (`keep_machine_settings`). Otherwise a restore could turn App Lock off, or store the key in a keychain the user stopped using. The copy's other settings come back with it.

The archive is encrypted when it has a key file (one written on its first open counts) or its key is given; not by its control, which can be what is damaged, nor by its stores' headers, which a damaged store garbles. A folder with no archive at all takes the copy's encryption and key file. When no archive is open and it is encrypted, the restore needs the archive's key, from its current password; without it the restore stops before anything changes (`archive-current-password-required`). An encrypted copy is opened with the password it was made with (`archive-password-required`); that password opens only the copy.

A move file from 0.5, which has five stores, is imported with the two agent-history stores empty. An import replaces the whole archive today, conversations included. Decided on 2026-11-15, not built yet: an import keeps the conversations this computer has and adds the file's, the same conversation once (BACKLOG `WORK-IMPORT-KEEPS-CONVERSATIONS`). Built: a move file no longer carries the safety copies, an import keeps this computer's, and the copies a file of 0.5 or earlier brings are added beside them (`data-model.md`, "Data migration bundle contract").

**What a restore or an import replaces becomes a safety copy** (the user's decision, 2026-11-15): `raw-snapshots/maintenance/before-restore-*` or `before-import-*`, listed for a restore as "Before a restore" or "Before an import", counted in disk usage, and listed in Free up space as a row of its own the user can tick (every copy is, and none is kept back by a hidden rule), never deleted on its own. Restoring it undoes the restore or the import. Before, it was a `maintenance.bak-*` folder in the archive's root that no screen showed and only "delete all data" removed, so every restore or import silently doubled the archive's size.

The install journal names the copy (`kept_as`), and only where this folder's installs put it: beside the other copies, under the random part of the journal's own backup folder name. The files are moved there and sealed after the new archive is published, so a crash after the publish still ends with the copy at the next start. The copy drops the search index, which a restore builds again, and a healthy restore leaves both live conversation roles in place and omits them from the displaced copy. A restore with damaged live conversations seals a full marked copy before publication and publishes it with the browsing replacement. Browsing restore accepts either kind of copy. A replaced folder that held nothing (an import into an empty folder) leaves no copy. One whose control cannot be read, so it cannot be sealed or restored, is kept all the same, counted and freeable, and not offered for a restore. A conversion from the old format still leaves its backup folder: it holds only the control the conversion replaced.

A move file this build writes is format 3: format 2 plus the two agent-history stores. 0.4 and 0.5 read only format 2 and refuse a format-3 file ("unsupported bundle format 3") before asking for its password. This build reads both, and refuses a file of a later format, or one whose archive schema is above its own, as `move-file-too-new` at the check, before asking for the password.

## A folder without `config.json`

Without a control, only what is in the folder can say whether an archive was ever there. `admission::census` decides, and it reads; it creates nothing.

| What is in the folder                                                                                                                                                                         | It is                                                                     |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Nothing, or the folder does not exist                                                                                                                                                         | A first run                                                               |
| Only empty folders                                                                                                                                                                            | A first run                                                               |
| Locks, the owner socket, logs, crash reports                                                                                                                                                  | A first run                                                               |
| What the scheduler keeps under `schedule/`, and the records under `audit/`                                                                                                                    | A first run                                                               |
| A staging folder an operation never finished (`staging/maintenance-*`), a leftover `.pk-durable-*` file                                                                                       | A first run; the next open deletes them                                   |
| Downloaded models, integration files, files under `exports/`                                                                                                                                  | A first run                                                               |
| Files at the top of the folder that the layout table has no name for (`.DS_Store`, an export the user saved there)                                                                            | A first run; the files are left alone                                     |
| A valid "delete all data" marker under the name PathKeep 0.5 wrote (`.pk-wipe-in-progress.json`)                                                                                              | An interrupted wipe (below)                                               |
| An install journal under the name PathKeep 0.5 wrote (`archive/.pk-import-journal.json`)                                                                                                      | An interrupted install (below)                                            |
| This build's install journal of an install that brings the control (`archive/.pk-install-v2.json`)                                                                                            | An interrupted install (below)                                            |
| This build's record of an archive being brought up (`archive/.pk-install-v2.json`, identity `pathkeep-create`), beside the folder its stores were made in, holding them                       | An interrupted install: a power cut took the stamped control (below)      |
| This build's "delete all data" intent (`.pk-wipe-v2.json`), beside the trash it names                                                                                                         | An interrupted wipe: a power cut took the control (below)                 |
| Any other record under the names this build writes (`.pk-wipe-v2.json`, `archive/.pk-install-v2.json`)                                                                                        | `archive-control-missing`: this build removes its control only after them |
| A PathKeep 0.3 import, rekey or restore journal, in a folder with no archive in the current format                                                                                            | An interrupted old-format operation (below)                               |
| Files the file manager writes into any folder a person opens (`.DS_Store`, `._*`, `desktop.ini`, `Thumbs.db`), at any depth                                                                   | A first run                                                               |
| Anything else under `archive/`, `derived/`, `raw-snapshots/`, `quarantine/` or `sidecars/`; a previous archive kept by a restore; an App Lock passcode; a half-finished old-format conversion | `archive-control-missing`                                                 |

Each row of the layout table (`vault-layout`) answers this question for its own file or folder, as it answers for every other operation (`CensusPolicy`): part of an archive, not part of one, or "whatever my folder says". A file the table has no row for takes the answer of the folder it lies in, and the data folder's own answer is "not part of an archive". Adding a row without answering does not compile.

Two properties have to hold, and a test holds each:

- **Whatever a finished "delete all data" leaves reads as a first run.** The test wipes a populated archive with automatic backup installed (removing the schedule writes a record after `audit/` is gone), a `.DS_Store` and an export in the folder, then initializes again.
- **Whatever the app creates on its first start, before anything is set up, reads as a first run.** The test starts the real desktop binary on an empty folder and classifies what it left.

An earlier version of this rule inferred the answer from the wipe policy ("an archive unless a wipe leaves it"). It missed, one after another, the scheduler's records, the staging folder of an import in progress, and the record a schedule removal writes during the wipe itself. Each miss would have locked users out with no way back, which is why the answer is now a column of its own.

Three things here differ from the first design, which said any unknown leftover means "recovery required":

- **Unknown files at the top of the folder do not count.** "Delete all data" does not remove an export the user saved into the data folder (a known gap in the wipe), and Finder writes `.DS_Store` into any folder it shows. Under the stricter rule a user who deleted everything could never start again. Initialization creates only paths the layout table names and removes nothing, so it cannot harm such a file. An unknown file _inside_ a folder the table owns (`archive/`, `derived/`, …) still counts: a wipe empties those folders, so anything there is not wipe residue.
- **Interrupted wipes and installs are recognized, not refused.** See the next section.
- **A staging folder nobody finished does not count.** Otherwise an import into a new data folder would refuse itself halfway, and a crash during one would lock the user out.

## Interrupted wipes and installs

PathKeep 0.5 and earlier take `config.json` away for a moment by design:

- "Delete all data" writes its marker, then removes the control first, then everything else.
- A restore, import or encryption change moves the control into a backup folder before the new one lands. Its journal records how to finish or undo that.
- PathKeep 0.3 did the same with its own import, rekey and restore journals.

A crash of one of those releases in such a window leaves an archive with no control and a record that explains why. Every release recovers from all of them automatically. A rule that refused every archive without a control would turn each of these crashes into a dead end, so the records are recognized, and such a folder behaves as it always has:

- Reading the config gives "not initialized", not an error. The recoveries are built on that: the wipe is finished at start and before initialization, a native install when the session opens, an old-format one when the shell asks for the upgrade assessment. A reader does not act on the record itself; the operation that wrote it may be running in this very process.
- The worker's command line lets such a folder through to the app, because the app it starts is what finishes the job. A scheduled backup would otherwise fail until someone opened the window.
- A wipe marker that does not decode is not acted on. The marker is written whole or not at all, so an undecodable one was not left by a wipe, and nothing else says the user asked for a deletion. The same goes for an install journal that is not JSON.
- When the control is present and needs a newer build, no record is replayed, whatever it says. Before this rule, a "delete all data" marker lying in a newer archive made an older build delete the archive at start; a test starts the real app on that folder and compares every file.
- A journal is still replayed next to a control that is merely damaged: rolling the install back is what puts the old control back.

This build never leaves a folder like that:

- **Its records have names those releases do not know** (`archive/.pk-install-v2.json`, `.pk-wipe-v2.json`) and carry an identity and a version that are checked before anything is replayed. A record this build did not write in that shape deletes and replaces nothing. A 0.5 that starts on the folder halfway through an operation of this build does not find a record to act on, and since this build stamps every archive it opens, 0.5 stops at the config of any archive this build has used.
- **An install never takes the control away.** The control is copied into the backup, not moved, and replaced by one rename on install; a rollback writes it back from that copy. An install that would leave no control is refused before it starts. Two folders have no control while this build's journal is there, and both are interrupted installs, not archives that lost their control: one the install brings the only control to (an import into a new folder, a restore repairing a folder that lost its control), until it lands; and one where a power cut on exFAT or FAT32 during the rename over the control left none, which those file systems do not do in one step. Recovery decides from what is there: the backup's copy of the control comes back where it holds what the control held, and a control the install brought goes with the rest. Before the copy exists nothing says the control was the journal's, and nothing changes. An earlier version refused every such folder at start (`archive-control-missing`), and nothing settled it.
- **The control is the first file an install puts in place and the last a rollback takes away.** PathKeep 0.5 opens a folder whose control is missing or has no stamp (an import into a new folder; a restore into a 0.5 archive this build could not bring up). Between two steps of an install it would find stores of the new archive under no control that keeps it out, and open them. The journal lists the control first and a rollback goes in reverse, so at no cut of either is a file of the new archive in place without its control. An earlier version followed the order of the layout table, which lists the stores before the control.
- **A published install is checked before its stage and its backup go.** The published journal says the install finished in the folder it was written in. This folder may be a copy of it, made by a tool that copied some files before the publish and some after: the new store may then be only in the stage, or a log the install removed may be back beside the new store, where SQLite would read the two together. Before anything is removed, every staged file must be in place holding what was staged, or, with nothing in its place, still in the stage holding it, and it is moved in; every file the install removed must be gone from its place, or hold what it held, and it goes back into the backup (into the quarantine, if the backup holds a name of it already). A staged file in place whose stage still holds it may be one file under two names (below): the stage's name goes into the quarantine. Anything else stops recovery with every record kept. An install finishing in the same call has had no gap in which anything could change, and does not read the files again.
- **A journal acts only on the files it moved, and only on whole ones.** Where a file is says what the install did with it, and what it holds confirms it. The backup folder is made, under a new random name, when the install begins, and only the install moves anything into it: an entry the backup holds is an original the install moved out of its place, and one it does not hold was never moved or has been put back. Before anything moves, the journal records what every file in place held and what every staged file holds, every byte (`vault-core/src/content_identity.rs`: SHA-256 over the file in 64 MiB chunks hashed in parallel; for a folder, over the exact name and what it holds of each file and symlink in it, every field behind its length so that no name reads like two entries, not over its own times or the `.DS_Store` a file browser drops into it). A rollback puts back only an original that still holds what it held, leaves in place only a file that holds the original, and takes out of its place only the staged file. A copy of the folder cut short while it copied the backup leaves a shorter file under the original's name: putting it back would leave a damaged store and delete the whole staged one with the stage. A copy that left an original out leaves the staged file in place with nothing saying the original was put back: leaving it would roll everything else back around a store of the new archive. Both, and anything else in a place, stop the rollback before anything moves, with the journal kept. The control binds the journal to its folder: the journal records the control's bytes before and after the install, and a rollback starts only where the control is one of the two. Every install moves `config.json` and every archive has its own, so a journal carried into another archive's folder, even with the backup folder it names (two folders merged, or the journal's files restored over another archive), meets that archive's control and changes nothing. A faithful copy of the whole folder, made by any tool, with or without the files' times, recovers like the original.
- **Every step of a rollback is one rename or one atomic write, and no move replaces anything.** A file taken out of its place is renamed into the stage under a name nothing has, and the stage goes with the journal at the end, so a rollback cut short never leaves half of a folder, and the next start finishes it. Moves into a place use the system's rename that fails where something is (`renamex_np` with `RENAME_EXCL` on macOS, `renameat2` with `RENAME_NOREPLACE` on Linux, `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` on Windows), so a file a sync client or a person put there after recovery looked stays, and the move fails. A file system that rejects the flag gets a look and then the rename. Only the control's rename on install replaces, by design.
- **A file another program holds is waited for, briefly.** Windows refuses to rename or delete a file another program has open without delete sharing, and an antivirus scan, the search indexer or a sync client opens a file for a moment right after it is written, which is when PathKeep moves it next. Every move and delete PathKeep makes of its own files goes through the `vault-fs` crate, which tries again on those errors (access denied, sharing and lock violations): each step of an archive operation (the install, the bring-up, "Delete all data", a restore's staging, an import, the conversion from the old format, the recovery of an operation PathKeep 0.5 left unfinished, "Free up space"), every write through `durable_io`, and the files the rest of the app writes and replaces: the semantic index and the in-app model, the search index's commits and generations, a backup's staging, Insights' blobs, the agent-history archive, schedule records, diagnostics. Each wait is 25 ms longer, ten more tries, about 1.4 s in all, the budget SQLite uses for the same errors. A program that holds the file longer still makes the operation fail, as before: before its commit it is undone, after it the next start finishes it. Two cleanups that try again on their next pass do not wait, because a reader keeps those files open for as long as it reads and a wait would hold up the work beside them on every pass: tantivy's garbage collection, which keeps a file it could not delete, and the semantic index's trash.
- **A file is flushed through a handle that may write.** Windows flushes a file only through a handle with write access: `FlushFileBuffers` requires `GENERIC_WRITE` (Microsoft's documentation), and the kernel refuses a handle with neither `FILE_WRITE_DATA` nor `FILE_APPEND_DATA` with `STATUS_ACCESS_DENIED` (seen in ReactOS's `NtFlushBuffersFile`). PathKeep 0.5 and earlier opened files they had written read-only to flush them before a rename: the stage of every install (a restore, an import, an encryption change, the conversion from the old format), a restore's staged copy, a safety snapshot's databases and seal, a move file before it is put in place, and a semantic index generation. On Windows each of those would fail with "access denied" and change nothing. Those flushes now open the file for writing on Windows and read-only elsewhere, as before (`durable_io::open_to_flush`, the store's snapshot, `agent-history`'s own key and format files). Found by reading the code against the documentation (2026-11-16); not yet run on Windows, where the `platform-native` workflow's Windows job runs the archive tests.
- **A file under two names is not deleted under one of them.** On exFAT and FAT32 a power cut during a rename can leave the file under both names, pointing at the same data; deleting one frees data the other still uses, and the next file written there overwrites the archive. A rollback that finds an entry in place and in the backup while its staged or discarded name is still there, or finds the original in place beside its copy in the backup, keeps the original in place and moves the entry's other names that may share its data into the quarantine (`quarantine/maintenance.bak-*/`), counted by the storage screen and freed by the user, instead of deleting them with the stage and the backup. Where the staged file is in place instead, it leaves its place under a name of its own, and its names go together with the stage. The control in place is moved away, not written over, while its staged twin is still in the stage.
- **A publish that reports an error is not rolled back in memory.** It may still have put the published record on disk (the flush after its rename failed). The install stops where it is, and the next recovery goes the way the record on disk says. Rolled back in memory, the files would go back while the record says published, and a later recovery would finish the install over them: databases of one generation beside a control and a key file of another.
- **No file numbers, and no length and time.** An earlier draft recognised the files by inode number. Measured on macOS disk images, exFAT and FAT32 give an empty file a new number at every move and every mount, and Linux numbers vfat and exfat files afresh at every mount, so after a crash and a reboot such a drive could never have been rolled back. The next draft used length and modification time, which survive a rename and a remount everywhere but tell nothing apart that is as long and was written within the file system's time resolution, and change in a copy made without times: a rollback then took another file for its own, or refused its own. What a file holds is the same on every file system and after every faithful copy.
- A file that was there before the install and is now neither in place nor in the backup stops the rollback with the journal kept; it is not reported as rolled back. The journal records its stage and backup relative to the folder. A 0.5 journal records no identities: it is rolled back only when the backup folder it names, randomly named when the install began, is in this folder, and its absolute paths are taken relative to where its backup was. Beside a stamped control it is set aside unread (`archive/.pk-import-journal.legacy-stale.json`): 0.5 cannot open a stamped archive, and this build replays a 0.5 journal before it stamps one, so it was carried in.
- **Moves are made durable destination first, and what that guarantees depends on the file system.** New folders' entries are flushed before anything is moved into them, and a move flushes the destination's directory before the source's. On a file system with a journal (APFS, ext4, NTFS) a rename is one step: a power cut leaves the file in one place or the other. On FAT32 and exFAT it is not, and no order of calls can make it so: the system may write the source's folder first, and a write to the allocation table cut short can lose a file wherever it was. On those drives PathKeep keeps every name that may share a file's data and stops instead of guessing (above), but a file a power cut lost there is lost. Telling the user when the data folder is on such a drive is in the backlog (`WORK-FAT-DATA-FOLDER-NOTICE`). An earlier version of this page said a power cut could leave an entry "in both places, never in neither", on any file system.
- **The records name paths the same way on every system.** Every path in the install journal, the creation record and the "delete all data" intent is relative to the data folder: plain names joined by `/` (`vault-core/src/recorded_path.rs`). A data folder on an external drive moves between Windows, macOS and Linux with its records; written with the system's separator, a record made on Windows would name `archive\history-vault.db`, which macOS reads as one file with a backslash in its name. No name in a record holds `/`, `\`, `:` or NUL, and a record holding one does not decode, so the operation it belongs to stops with nothing changed. A name a record cannot hold stops the operation before its record is written: a file in `archive/` with a backslash in its name stops "Delete all data", and the error names it. PathKeep 0.5's journal keeps the native absolute paths that release wrote, and is read as before.
- **"Delete all data" keeps the control until the very end, and deletes nothing until everything is moved aside.** Order: the intent an earlier wipe left, settled; a trash folder in the data folder (`wipe-trash-*`), then the intent; `config.json` replaced by an empty, not-initialized one with a stamp, the archive's or, where it had none, this build's (every background worker stops when it sees that; 0.5 takes a not-initialized control without a stamp for a first run); the workers stopped; every target recorded in the intent, sorted so that a store's main file comes before its `-wal` and `-shm` (only "not found" means a target is not there: one the wipe cannot look at stops it here, since left out it would stay while the rest moved, and an undo would move it out as something the wipe did not record); every target moved into the trash in that order, each by one rename, including a leftover `.pk-durable-*` temporary file in the folder (a crash during an atomic write can leave a full copy of the old settings there); a scan for anything outside the trash that still means an archive, by the same rule as a folder without a control; the commit, which rewrites the intent to say everything is in the trash; the trash deleted; the keychain; the automatic backup; the intent; `config.json`. Before the commit a failure puts everything back in the same call, and a crash leaves the same to the next start: nothing is deleted. After the commit the next start finishes the wipe. A commit whose write reports an error may be on disk all the same (the flush after its rename failed): the wipe stops where it is and says so (`archive-wipe-stopped`), and the next start goes the way the intent on disk says. Undone in the same call, the files would go back while the intent says committed, and the next start would delete them. A crash after the intent is removed leaves an empty, not-initialized control in an empty folder; setup writes its first control over it without that stamp, which described no archive, and the new archive is stamped once its stores exist. Where there was no control, the empty one is written before the intent, so the intent never lies alone.
- **The intent acts only in the folder it was written in, and undoing it gives the archive back whole.** It records the control the user confirmed deleting and the emptied control the wipe writes, both byte for byte, the trash it made, and every target. A wipe cut short is settled only while the folder holds one of the two controls, or none beside the trash the intent names: on FAT32 or exFAT a power cut during a write in the folder can leave no control, and the trash, made before the intent under a random name and removed only after the confirmed control is back or once everything in it is deleted, says the intent is this folder's. Without a control the intent puts back the one the user confirmed, or finishes. Beside another control (a folder restored from a backup, imported into, or an intent carried in) the intent is moved, whole and under a name nothing has, into the quarantine (`quarantine/wipe-trash-*/`): it is the only copy of the control the user confirmed deleting. Nothing else is touched; its trash, if it is here, stays as it is, and the next "Delete all data" lists it. With no control and without its trash, nothing binds the intent to the folder: the folder is refused as one whose control is missing (`archive-control-missing`), and the intent stays as it is. An earlier version deleted the intent and wrote that control into the trash, over anything of the same name there. Undoing puts every recorded target back, in the reverse order of the moves: a store's companions come back before its main file, so at every cut a main file in its place has its own `-wal` and `-shm` beside it, never a mix. A main file in its place while a companion of it is still in the trash is no cut of a wipe or of its undo: something was put there since, and the undo stops before anything moves. What stands in a target's place now, and anything at a target the wipe did not record, is moved into the trash's `displaced/` folder, never deleted, and never left in the archive: a store beside another store's `-wal` or `-shm` would be read with it. A recorded target in neither place stops the undo before anything moves, with the intent kept: an empty trash is not proof that everything is back. Then the confirmed control comes back over the emptied one. A trash that still holds files, or a `displaced/` folder even with nothing in it (an empty folder under two names after a cut rename on exFAT has data of its own), is kept, and the next "Delete all data" lists and removes it. Finishing deletes the wipe's own trash, never what stands at a target: a commit proves the user confirmed deleting what is in the trash, and after a crash the folder may have been offline and hold what the user put back since (a restore from a backup). What still means an archive outside the trash is logged and left where it is; the folder then reads as an archive without a control (`archive-control-missing`). An earlier version deleted it whenever the control was the emptied one. A copy of the folder made during a wipe is the same folder to the intent: undone before the commit, which gives the copy its archive back, and finished after it, which deletes the copy's copy of what the user confirmed deleting. An intent that names as its trash anything but a `wipe-trash-*` folder directly in the data folder is refused (`archive-control-invalid`). The earlier drafts told a copy from the original by the inode numbers of the archive's databases, which exFAT, FAT and network shares do not keep; nothing depends on them now, since nothing is deleted on the record alone. Import, restore and conversion settle a pending wipe before they install anything, as initialization does (which then recovers an install whose record the undone wipe put back, under the owner lock), and refuse while one is pending. A second "Delete all data" settles it too, before its own intent could replace one that still names keys to clear.
- **A 0.5 marker is finished only where there is no control.** It records nothing of the kind. PathKeep 0.5 removed the control right after writing its marker, before deleting anything, so beside a control, stamped or not, its wipe had deleted nothing: the marker is discarded, and the user still sees the archive and can delete it again. Without a control it is finished as that release would have: deleting in place.
- **Nothing writes a control into a folder the wipe is emptying.** The wipe holds the control's gate (below) from reading what to delete to its last removal. A settings save waiting for it then finds no archive and is refused (`archive-reset`) when the settings it was given were read from one; a provider key or an automatic backup waiting for it is refused too, so none is left behind.

**What these records do not cover.** Each of these is known and accepted for v0.6.0:

- **A program writing into the data folder while a recovery runs.** Recovery decides every step from what it reads first. Moves never replace, so nothing put into a place in between is deleted; a file swapped in between two reads is not caught, and a file system that rejects the no-replace flag leaves the instant between the look and the rename.
  - **An external restore during an install can block reopening.** If the journal recorded a missing member and another tool returns a file at that name, install refuses to overwrite it. Rollback and subsequent opens refuse the unexpected bytes. Stop the external tool and PathKeep. Make a filesystem copy of the entire data folder, including `archive/.pk-install-v2.json` and its named stage and backup. On a working copy, set aside the unexpected members whose names the journal recorded as absent. Leave originally present members in their recorded places. Reopen the working copy to let rollback finish. Keep the returned generation for separate recovery.
  - **A crash after a concurrent replacement has been moved can also block rollback.** The journal can still identify A while its backup directory holds B. Both the refusal and the repeated startup failure protect B. Preserve the whole folder as above and keep B separately. If the exact A recorded by this install is available, put A at the corresponding backup member on the working copy and let PathKeep replay the journal. Otherwise recover a complete known-good archive in a separate folder and retain the contested folder for recovery. Editing the journal or discarding its backup destroys the evidence needed to distinguish these generations.
  - **An external restore of only a conversation WAL can hide committed messages.** The main database can retain its identity while `-wal` disappears or belongs to another copy. A later safety copy can then omit committed frames, or the pair can fail to open. Stop the restoring tool and quiesce writes. If the last readable WAL is still held open, preserve its bytes with the matching main file before closing that process. Keep every candidate generation separately. With PathKeep closed, recover on a separate copy using a main database and WAL from one consistent backup, together with its matching conversation role and encryption material. If the original WAL and all consistent backups are gone, messages present only in those frames cannot be reconstructed from the main file.
- **The keychain and the automatic backup after an old committed wipe.** They are not in the data folder. A committed intent carried into another folder never clears them, because that folder's control is not the emptied one; but the same folder opened again after the user set up another archive elsewhere clears the keychain entries by provider id, which the new archive may use too.
- **A creation record carried into another stamped archive that lost a store.** The record's store, made with the first archive's key, is moved into the second's empty place and does not open there. Nothing of the second archive is overwritten or deleted.
- **A record carried in together with what binds it, into a folder without a control.** There, the trash a wipe intent names and the stores in a creation record's folder are what say the record is this folder's. Copied into another data folder along with them, while that folder has no control, the record writes its own archive's control there, and an undone wipe puts its own files back where that folder has none, moving what stands in their way into its trash. Nothing of that folder is deleted.
- **What a power cut on FAT32 or exFAT loses.** Above: names that may share data are kept, and recovery stops where it cannot tell, but a file the cut itself lost is gone. One place keeps only one of two such names: a finished install whose recovery finds an old file both in its place and in its backup moves the one in place to `quarantine/`, and the install's cleanup deletes the backup. On FAT32 or exFAT those can be two names of one file only if a copy of the folder was taken during the install, recovered, and cut by a power cut at that one rename of the recovery; the quarantined name then points at freed space. A disk check before freeing quarantine on such a disk repairs it, as for every quarantined name there.
- **A folder merged into another archive's folder while a wipe is unfinished.** An undone wipe knows each target only by where it is: what stands in a target's place is taken for the file the wipe left there. A wipe cut short, its folder then merged into the folder of another, complete archive by a copy that stops partway (the trash's main file copied, its `-wal` not), puts the main file back beside the other archive's `-wal`. Merging one archive's folder into another's is not something PathKeep, Finder, Explorer, Time Machine or Migration Assistant do (they replace a folder); a wipe cut short and started again in its own folder is covered by the order of the moves.
- **Hard-link copies of a running data folder.** The stores a creation record made and the stage an install record staged are removed without checking what they hold since. A hard-link copy (`cp -al`) taken during the operation shares those files with the original; if the original then went on, wrote into them and was deleted, opening the copy deletes them. Copy and backup tools copy bytes or snapshot the disk; none links to the files of a running folder.
- **Moves within the data folder only.** Stage, backup, trash and quarantine are all in the data folder. A folder in it that is a mount of another disk cannot be renamed out of its place (`EXDEV`): the operation fails before anything is deleted, and is undone.
- **Two names deleted together.** Where both names of a file leave the archive (a staged store discarded with the stage), they are deleted in one folder removal. In the instant between the two deletions a program allocating on the same exFAT disk could take the freed space; a disk check after the power cut repairs it.

## Who writes `config.json`

The control holds settings and the archive's own state (whether it is set up, its mode, its stamp). Several things write it, some of them operations that take minutes. They follow one rule: every write is a read-modify-write under the control's gate (`vault-core/src/config/control_gate.rs`), and each writer changes only the fields it owns, on the control as it is when it holds the gate. `save_config` takes the gate as an argument, so a write without it does not compile.

| Writer                                       | Owns                                                                                                                                             |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Settings save                                | The settings it was given, as changes against the settings the window showed. Never whether there is an archive, never the mode                  |
| Menu bar icon, App Lock passcode             | Their own fields                                                                                                                                 |
| Setup                                        | Every setting it was given, and `initialized`; over a control that was not initialized, no stamp                                                 |
| Bring-up to this build's layout              | The stamp                                                                                                                                        |
| At-rest repair (at launch, and the command)  | The mode, from the files' headers                                                                                                                |
| Mode change                                  | The mode, on the control as it is at install time; then whether the key is remembered                                                            |
| Restore                                      | Everything but this machine's settings (App Lock, whether the key is remembered) and the encryption mode, which stay as they are at install time |
| Import                                       | Everything but this machine's settings (App Lock, whether the key is remembered), which it takes from the control as it is at install time       |
| Conversion from the old format               | The settings it was given (setup's, or the upgrade screen's)                                                                                     |
| Install recovery, old-format launch recovery | What the interrupted operation recorded                                                                                                          |
| "Delete all data"                            | Everything, from start to end                                                                                                                    |

The gate is held for the file only: never across database work or a wait on another lock, and taken after the archive's operation gate by those that hold both. That is why a settings save never waits for an export, a snapshot, a retention prune or the copy of a mode change, restore or import, which hold the operation gate for minutes: those take the control's gate only for their own write at the end. An operation that rewrites the archive builds the replacement's control at that moment from the live one, so a setting saved while it ran is kept. A conversion is the exception: it installs the settings it was given, because setup's choices are what it writes, and nothing else changes settings while the upgrade screen is up.

An operation that closes the archive to put another generation in its place (a mode change, a restore, an import, a conversion) holds the session's maintenance lease from before it closes the archive until the replacement is published (`VaultSession::begin_maintenance`). An open in the same process meanwhile waits and gets the replacement, or what is on disk when the operation ends without one; a close waits and closes the replacement. Without the lease, an open between the close and the publish took the files being moved, or replayed the operation's install record while it was being written: the owner lock does not stop it, because the operation and the open are in the same process.

The settings page saves each change against the settings it showed (`baseConfig`), so a save carries only its own changes. A save whose settings came from a set-up archive, into a folder that has none any more, writes nothing (`archive-reset`); a save never sets an archive up (`archive-uninitialized`).

## Where the decision is made

Three functions in `vault-core/src/admission.rs`, all read-only:

- `inspect(root)` classifies a folder: admitted, first run, interrupted, or refused with a reason.
- `require_control(root)` is `inspect` for readers of the config: the control, nothing (a first run or an interrupted operation), or an error.
- `guard(root)` is the check before a write: a control that is on disk must be one this build may use. A folder without a control passes. Staging folders and snapshot destinations have databases before they have a control, and whether a control-less folder is a first run is `inspect`'s question, asked where the answer changes what happens.

A live `Vault::open` or `open_owned` requires an admitted `config.json` when the folder contains archive data. A recognized interrupted operation can account for a temporarily missing control. An empty folder passes admission: a direct first open uses the released browsing layout and creates its stores, without writing a control. Product setup saves the initialized control first, so that the first open can promote the layout and subsequent opens can identify the archive.

For an established encrypted archive, an authentication error reading a conversation page is local to that database once all browsing stores have verified the data key. Opening visits the pages needed for startup. A verification command needs to check the remaining pages explicitly.

There is no token passed from the check to the operation. Every boundary reads the disk again, which is the stronger guarantee: a token says what the folder was, and a restore or import may have replaced the control since.

| Entry point                                                                          | Check                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Desktop start                                                                        | `inspect`, before the window, the owner lock, folders, logs, recovery, keychain, App Lock. Again after recovery, under the lock.                                                       |
| Worker command line (backup, doctor, MCP server, …)                                  | `inspect`, before the schedule's logs are trimmed or the app is started                                                                                                                |
| Requests the owner serves                                                            | No check of their own: every route that uses the archive reads the config first. The scheduled backup, which records its attempt before reading the config, checks before that record. |
| `load_config`                                                                        | `require_control`. Never a default for a file that is there.                                                                                                                           |
| `save_config`, creating the folder layout                                            | `guard`; a save writes the stamp on disk back unchanged, but setup over a not-initialized control writes none                                                                          |
| Opening a live archive, password open, staged open                                   | `require_control` for a live root, `guard` for a stage, before the owner lock or a key envelope                                                                                        |
| Finishing a wipe                                                                     | `inspect`                                                                                                                                                                              |
| Replaying an install journal, old-format launch recovery                             | Refused only when the control needs a newer build                                                                                                                                      |
| Old-format conversion                                                                | `guard`                                                                                                                                                                                |
| Mode change, password change, snapshot, export, retention, checkpoint replay, backup | `guard` again when the operation starts (`Vault::recheck_root`)                                                                                                                        |
| Restore and move-import                                                              | Target: refused only when its control needs a newer build. Source: its own control is decided before anything is staged in the target.                                                 |
| Keychain reads and writes, provider keys, installing or removing the schedule        | `guard`, before the machine is touched                                                                                                                                                 |
| Standalone agent-history command line                                                | Refuses any folder that has a PathKeep `config.json`                                                                                                                                   |

A restore over a damaged or missing control is allowed, because that is what a restore repairs. A restore over a control that needs a newer build is not: that archive is intact, and replacing it would put an older one on top.

A copy of an archive (a snapshot, a staging folder for a mode change, an export) carries the stamp of the archive it was copied from.

### What a refused start does

- Started in the background or by the scheduler: the process exits with status 1 and the reason on stderr.
- Started by a person: no window is created. A native dialog gives the reason in English, Simplified or Traditional Chinese (picked from the OS languages, since the config is the thing that could not be used), with the folder and the code, and the app quits when it is dismissed.
- A refused start does not register as "the running PathKeep" for the data folder. Otherwise a newer build started while the dialog is still open would hand over to the refused one and show nothing.
- **Gap, to close before v0.6.0 ships:** the dialog is all there is. For an archive that needs a newer build the screen that replaces it should offer the update. For a control that is damaged or missing it must lead to restoring a safety snapshot: the backend still lists snapshots and restores over a damaged control, but with no window nothing can ask it to. Until then that user is safe and stuck. Tracked in `WORK-ARCHIVE-REFUSAL-SCREEN`.
- Guaranteed untouched: every file and folder under the data root, including the lock files and logs; the keychain; the schedule; App Lock state.

One exception is outside the app's control: on macOS a schedule installed by an earlier run redirects the worker's output into `schedule/logs/`, and launchd opens those files before the worker starts.

## What is proven, and how

- `vault-worker/tests/root_admission/operations.rs` drives every entry point in the table against an archive stamped for a newer build, through the real owner and the real worker binary where the entry point is one. Each case hashes the whole data folder, the test keychain and the test scheduler before and after, and counts keychain reads. The list of entry points is written out by hand; `registration.rs` fails when a command is registered without a row.

- `src-tauri/tests/root_admission_startup.rs` starts the real desktop binary: a background start and a cold worker start on a newer archive leave the folder unchanged, an interrupted-wipe marker in a newer archive deletes nothing, and whatever a first start creates still reads as a first run.
- `vault-core/tests/root_stamp_codec.rs` holds the byte-for-byte rule for the stamp across a setting change and a mode change, the version rule against every ordering of level and floors, and that a bare `archiveMode` is written back as v0.5.0 expects.
- `vault-core/src/maintenance/creation/tests.rs` cuts the bring-up at each of its three durable points and opens again; has a 0.5 store open the folder after a crash before the stamp and save into a store the record names; refuses a stamped archive missing a browsing store, and a record naming a file that is not a store, comparing every file before and after; restores a snapshot and imports a move file that 0.5 would have written (five stores, no stamp, format 2); and keeps a later build's revision-2 stamp byte for byte through an open, a settings save, a mode change and a restore. ## The shape of what is persisted

A format change that nobody noticed is the usual way two versions come to disagree: a field is added to a record, the build that added it writes it, and an older build drops it on its next save or reads a default where a value was. So the shape of every JSON control record is generated from the types that are actually serialized (`vault-core/src/persisted_schema.rs`, with `schemars`) and compared to a snapshot in the repository:

- `src-tauri/crates/vault-core/tests/persisted_schema/revision-N.json` is the snapshot for revision N. Any change to a listed type fails `tests/persisted_schema.rs` until the snapshot is rewritten, so the change shows up as an edit to that file in the same commit and in review.
- `formats.json` beside it has one entry per revision: what changed and what older builds do with it. Its `released` list ties a revision to the hash of its snapshot. Once a revision is listed there its snapshot cannot change at all; a shape change then needs a new revision. The check needs no git history.
- Its `releases` list says which revision each published version writes, prereleases included. `scripts/verify-archive-formats.mjs` (part of `release:check:config`, so of every `bun run check`) fails when a newer version writes a lower revision than an older one (users who update would find their archive refused as too new), when a listed version writes a revision that is not frozen under `released`, and when this build writes a lower revision than a version already published. Versions are ordered as semantic versions, not as text.
- The snapshot is for the revision this build writes. Until a release writes it, it may be edited in place.

Records in the snapshot today: `config.json`, the install journal, the "delete all data" marker, the two App Lock records, a snapshot's file list, a move bundle's manifest, a scheduled run's attempt record.

Not in it yet: JSON stored in database columns, the search index's and vector index's own manifests, the portable-artifacts origin record, the old-format conversion state, the import-roots record, crash reports, and the standalone agent-history marker. Binary formats (the key envelope, the encrypted bundle entries) have their own golden bytes. A snapshot cannot see a change of meaning that keeps the shape, such as a default or a unit; that still takes a person.

## Changing the format later

Revision 1 is the first stamp, so the bring-up starts only from an archive without one. The next format change keeps the same order and extends it:

- Publish the higher stamp first, then write the first byte of the new format. Never lower it again.
- Bring an archive up from a lower stamp as well as from none: record the stores the new layout requires, stamp, create, remove the record (`maintenance/creation.rs`).
- A new move-file format number for a layout with new stores (`FORMATS` in `migration/native.rs`).
- When a release is cut, its revision and the hash of that revision's snapshot go into `formats.json` under `released`, the revision's entry says `released`, and the version goes under `releases`. The Release workflow runs `verify-archive-formats.mjs --releasing <version>` and stops otherwise, and also when the persisted shapes are a revision ahead of what the build writes (a format change half done).

### Conversation protection and repair in revision 1

Browsing restore keeps the live conversation roles, including a missing role. It accepts
a copy marked with unreadable conversations and verifies the browsing members it will use.
During damage it seals a full copy of the displaced browsing generation and the opaque
conversation files before installation. The install journal normally publishes this copy and the
replacement together. A copy containing a displaced open handle is published before
owner close so rollback cannot discard the only remaining readable generation. While the OS can read the files, their contents can be protected
even if Turso cannot open them. A filesystem read error stops publication of a complete copy.

Conversation repair is a separate preview and execute operation on an unlocked,
partially available archive. Copy repair checks the listed source, its file proofs,
the two role schemas, their pairing tickets, the retained raw bytes and the read model.
Legacy sealed copies and marked copies can supply independently verified evidence for a private offline rebuild.
Start-fresh and copy repair clear the device's selection reference and pending first save.
The next capture requires reviewed roots. A rebuild keeps the device grant and capture
receipts. It reparses a disposable evidence copy, restores the canonical user-state mirror,
and installs the verified pair under the current key. Interpretation IDs may change.
No parser opens a tool folder during the rebuild.

For a reader-only repair, preview attaches the live conversation service before taking the reviewed checkpoint. In a recovered archive without a device grant, first attachment parks damaged reader tickets and can start initial search preparation. Preview waits for that preparation to finish. The safety copy and installation still check the exact reviewed identities.

### First-run drafts and task acknowledgements

`config.onboardingChoices` is optional and bound to the installation alongside capture preferences. It can exist before the archive databases. A release-0.5.0 reader of an unstamped first-run control ignores the extra field and may drop it when saving. Released readers refuse an initialized, stamped revision-1 archive. On this installation a restart restores the draft. Setup consumes it, portable controls and safety copies omit it, installing an initialized archive clears it, and wiping the control removes it. The selection grants no source-directory access.

Archive migration 24 adds `runs.task_dismissed_for`. Intelligence migration 3 adds the corresponding nullable field to `intelligence_jobs` and `ai_jobs`. Existing rows have no acknowledgement. The run stores its finish stamp; reusable queue rows store the attempt number with its finish or update time. The state/type indexes serve the rail's counts. The fields follow their owning database through open, snapshot, restore, password and encryption changes, and wipe. A move carries the browsing run ledger; the destination rebuilds the Intelligence database. The maintenance row fixtures exercise these columns. Export progress, cancellation and the task event subscription live only in the owner process.
