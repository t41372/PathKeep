# Large-result keyword search: research report (2026-10-04)

> Measured by Codex (GPT 6 astra) for [large-result-search-tradeoff.md](../large-result-search-tradeoff.md). Links to `results/`, `src/` and other prototype files point to the research checkout, which was not kept.

Use a rebuildable Tantivy sidecar for relevance ranking, preserve exact filter and URL-group semantics, and run exact counting separately. On the complete 14.4M-visit fixture, Tantivy returned the first and next 100 common-word results in 54.55 / 53.41 ms with recency breaking relevance ties; its separate exact page count took 3.08 ms. The simpler score-only Block-WAND path took 6.27 / 6.15 ms, but that changes the tie order. Tuned FTS5 took 1,132 / 1,156 ms and 267 ms for counting in the narrower engine benchmark. No candidate window is necessary. This supports a Tantivy integration experiment, not a claim that every query is fast or that the 4-core, 8 GB target is certified: duplicate-URL grouping, full product scoring, cold encrypted reads and target hardware still need validation.

## What was actually measured

The generator in `src/fixture.rs` reproduces the constants, LCG, URL skew, 3 profiles, 20,000 domains, titles, URL strings and integer timestamp step from `archive_scale_bench.rs`. It physically writes **14,400,000 visits and 3,600,000 URL records** inside this clone. There are **2,865,791 URLs with visible visits**. The rare query is `page 1200001`; the profile is profile 1, Chrome Default; the domain is `site42.example`. Last-seven-days uses the fixture's ending date, not today's date.

The archive uses a compact SQLite schema with real visits and indexes, not PathKeep migrations. FTS indexes one combined URL/title field with external content. Tantivy indexes that same text, metadata and a numeric 2/3/4-character prefix field. Both reproduce the product benchmark's seven tested match counts, including 73,731 for `topic 42` and 6,853 for `topic 421`. This is **not a full port of PathKeep's two FTS mirrors, field weights, normalization, CJK, annotations, enrichment or operator syntax**. Tantivy's prefix-field BM25 differs from FTS prefix scoring, and its BM25/length encoding differs from SQLite. Cross-engine rank equivalence was not asserted.

One fixture URL occurs in only one profile. Grouping is therefore naturally one result per URL here. General cross-profile URL-string grouping is a required integration task, not something this fixture proves. Counts in this report are exact matching **pages**, not matching visits. The measured date predicate is valid because the interval ends after the fixture's latest visit; a latest-visit field alone cannot answer arbitrary historical intervals.

Release build: Rust 1.96.0; Tantivy 0.26.2; rusqlite 0.39.0 with bundled SQLCipher/OpenSSL (SQLite 3.50.4). Hardware: **Apple M5 Max, 18 logical CPUs, 64 GB**, macOS 27.0.1, SSD. Index construction uses four workers and a 256 MiB writer budget; query experiments use one merged segment. This does not simulate a 4-core 3 GHz / 8 GB machine or memory pressure.

Every timed sample records `uptime`, elapsed time, Rust heap peak, SQLite allocation peak and process lifetime RSS high-water mark. Three samples per query/page/count; tables show medians. Index builds and mutation actions are single observations. The first FTS and index builds overlapped; the final `*-repeat` query suites ran sequentially. Other jobs remained active. Load averages ranged roughly 6–52, and free disk changed substantially because other jobs shared the volume. The final FTS/Tantivy/cached-encryption comparison ran around load 19–26; later recency experiments ran around 6–14. Do not interpret small differences or the occasional faster encrypted result as causal speedups.

No OS cache purge was performed. Page timing includes query construction, ranking, offset handling and fetching the displayed rows; it excludes opening the index. Tantivy fetches stored row data; FTS performs at most 100 metadata lookups after ranking. Neither includes IPC serialization or canonical grouped hydration. Next page reruns top-200 and discards the first 100, under an unchanged snapshot. The rare query returns one row then none; the domain query returns 100 then 45.

`results/*.jsonl` retain individual timings, load readings, counts and page IDs; `results/summary.json` contains medians, extrema and memory. `summarize.py` checked matching counts, no duplicates/overlap, encrypted/plain page identity and pruning results against exhaustive top-200. The final run passed 483 evidence checks, plus four mutation-visibility checks. An additional mutation check initially exposed NULL timestamps for two unvisited URLs after fixture cleanup; it was fixed with `COALESCE`, rerun successfully, and the failed log is retained. Product code was not changed. Product E2E and `bun run check` were not run for this isolated Cargo project; release compilation, formatting, runner syntax and real-engine evidence checks passed.

## Why the techniques behave this way

**FTS5 does not provide competitive-score block pruning through a custom rank callback.** The instrumented constant rank was invoked exactly 3,600,000 times for unfiltered `topic ORDER BY rank LIMIT 100`. The direct unfiltered probe took 1,024 ms with BM25, 4,541 ms with rank, and 2,130 ms with the deliberately cheap constant rank. Those are separate-load diagnostics, not a proposed scoring function. Rank sorting delegates to an internal sorter; it can change overhead without avoiding scoring all matches. See [SQLite's rank sorter source](https://sqlite.org/src/doc/trunk/ext/fts5/fts5_main.c). The original product's documented 10.5 s first page / 26.6 s count includes both mirrors and visit/URL grouping; it was not reproduced as an IPC measurement here.

Full-detail prefix FTS occupied 749.0 MiB; removing prefix indexes reduced it to 482.2 MiB. Prefixes help expansion, not a whole-archive term. `detail=none` reduced it to 497.9 MiB but frequency scoring reloads/tokenizes content, and phrase/column capabilities are lost; `detail=column` was not separately benchmarked. `columnsize=0` was not measured because it removes the stored length fast path. `fts5vocab` is useful for planning, but the measured `topic` lookup still took 40.54 ms and included unvisited URLs. Precomputing statistics could remove repeated statistics work; it does not remove candidate scoring. These API restrictions are documented in [FTS5](https://sqlite.org/fts5.html).

**Tantivy has real Block-WAND, but query shape and ties matter.** Its [term weight](https://raw.githubusercontent.com/quickwit-oss/tantivy/0.26.2/src/query/term_query/term_weight.rs) uses block maxima; its [Boolean weight](https://raw.githubusercontent.com/quickwit-oss/tantivy/0.26.2/src/query/boolean_query/boolean_weight.rs) specializes eligible term unions and otherwise falls back to generic traversal. AND-prefix queries in this prototype do not inherit the single-term pruning behavior. The score-only common-word collector received 170 competitive callbacks for page one; this is not a count of every score evaluation. For recency ties it must admit equal scores, and the common-word advantage narrows to about 55 ms. The corpus has uniform short documents, so this tie issue is central, not an edge case. Group and secondary-sort bounds would need explicit engineering to prune those ties safely.

A stock Boolean-filtered `TopDocs` took 25.07 / 25.11 ms for `topic`, compared with 6.27 / 6.15 ms through the score-only eligibility collector. Conversely, stock domain intersection took 0.28 / 0.23 ms while the broad lexical collector took 33.76 / 42.87 ms. Use selectivity estimates and explicit query plans; do not route every filter through one collector.

**Exact counts are a separate query.** Tantivy's raw posting count was 0.21 ms but reported all 3.6M documents. Live/profile/date/domain predicates change that answer. Filtered Count took 0.08–10.63 ms in the final plaintext comparison. A materialized matching bitset is 450,000 bytes; an eligibility bitset needs the same. Intersections/popcount took 0.011–0.015 ms, after 38–45 ms to build eligibility and 0.034–2.36 ms to build matching bits. These construction costs are mandatory on a miss. General URL grouping requires group-ID dedup; page counts and visit totals are different operations. Tombstones invalidate raw posting lengths as live counts.

**Static blending** was measured as BM25 + `0.2*ln(1+visits)` + `0.1*normalized_recency`, traversing all qualifying matches. `topic` was 54.97 / 55.20 ms. Safe early termination must bound the lexical score, popularity and recency together. Reranking a fixed newest/most-visited subset is not exact. This formula is experimental, not a product recommendation.

**An owned impact/block-max index is not obviously simpler.** It still needs token positions, prefix/CJK behavior, conservative floating-point bounds, compressed postings, deletes, segment merging, encryption, corruption recovery and versioning. Store frequency/length bounds rather than stale final BM25 scores: corpus statistics change after backups. No general implementation was built, so no latency, build or mutation estimates are claimed.

**Time sharding** can shorten a date-restricted scan, but unrestricted search must consider every shard. Use global BM25 statistics, not incomparable shard-local scores. The same URL can occur in many time shards; summing counts or concatenating local top-100 results is wrong. Streaming can show provisional results, but final global order requires proving that no unvisited shard can beat the heap. The existing single index/segments are the simpler starting point; calendar sharding was not prototyped.

**Caching** should be bounded and keyed by generation, analyzer/scoring version, normalized query and every filter. A backup can change global document frequency and average length even when a cached document is untouched. The simple correct policy is invalidation on every canonical generation, rebuild only popular entries, and no TTL-based correctness claim. Bitsets were measured; persistent result-cache build, lookup and incremental maintenance were not. [Lucene's WAND implementation](https://raw.githubusercontent.com/apache/lucene/main/lucene/core/src/java/org/apache/lucene/search/WANDScorer.java) is a credible alternative, but its JVM integration was not prototyped.

## Encryption findings

`src/encrypted.rs` implements a **read-only experimental Directory** with authenticated AES-256-GCM blocks of 64 KiB. Metadata and data files are encrypted; file name, block position and plaintext length are authenticated, and the header is authenticated. File names and sizes remain visible. There are no decrypted disk files during encrypted querying. The plaintext input exists only to produce/compare this synthetic benchmark snapshot; that conversion workflow must not become an encrypted user's first-build path.

The encryption format added 150,396 bytes, about 0.043%. An uncached encrypted `topic` page through the pruning collector took 221 / 212 ms, versus 6.27 / 6.15 ms in the later plaintext run. A 64 MiB FIFO plaintext block cache reduced repeated reads substantially. Recency ordering then measured 54.89 / 51.62 ms, but the first request in that fresh process was **279 ms**. The pushed-filter recency process started at **611 ms**; the selective-domain cache refill also produced 110–149 ms samples. These are measured encryption costs, not a target-machine prediction. Cache policy, query-specific field loading and cold behavior need further work.

The prototype uses a fixed synthetic-data key and is not production security code. It has no encrypted writer, crash/rekey protocol, secure key lifecycle, cache zeroization, replay defense or security review. A production Directory must encrypt writer buffers, merge output, manifests and temporary files from creation; bound plaintext RAM, clear it on lock, authenticate generation/key IDs and use fresh nonces/keys appropriately. Rewrapping a sidecar data key can make a password change cheap; true data-key rotation requires rewriting encrypted bytes. Neither rekey mode was measured. A SQLCipher-backed chunk Directory is another way to reuse existing crypto/transaction infrastructure, but was not tested.

An encrypted filesystem can preserve mmap behavior, but full-disk encryption generally protects a locked device rather than enforcing PathKeep's archive password boundary. An app-managed cross-platform encrypted volume adds platform/deployment work. Neither filesystem approach was measured. FTS5 itself can live in SQLCipher; that also requires changing the current plaintext `ATTACH ... KEY ''` contract and handling journals/temp storage. No SQLCipher FTS performance is claimed.

## Recommended integration

1. **Keep canonical SQLite/SQLCipher authoritative.** Add a versioned, replaceable lexical index under `derived/`, with an analyzer version, score version, canonical generation and encryption key ID. Adopt Tantivy only through a reviewed architecture trade-off; this report does not override the accepted FTS design or authorize implementation.
2. **Preserve existing query semantics in `archive/history.rs`.** Keep syntax parsing and deterministic normalization; translate the accepted query AST to a typed search adapter. Port field boosts, term/trigram/CJK union behavior, exclusions, phrase checks, notes/tags and fallback semantics explicitly. Prefix materialization in this harness proves a match-set experiment, not production scoring parity. Keep FTS as a complete fallback while unsupported operators are ported.
3. **Preserve grouping in `grouped.rs`.** Canonical `url_id` is profile-specific; `urls.url` defines a page. Keep lexical records per `url_id`, attach a stable URL-group ID, and collect top-k distinct groups with a group score equal to the best qualifying member. The pruning threshold must come from the kth distinct group, not kth child. Do not dedup a fixed top-100/oversampled list afterward. For selected groups, hydrate matching visit counts and newest matching visit from every qualifying member. This avoids inventing matches by mixing title terms from different profiles into one text document.
4. **Apply filters to the same visible visits.** Do not intersect unrelated “profile present” and “date present” flags: they can describe different visits. Maintain rebuildable profile/day URL membership and boundary-day visit lookups, or an equivalent exact visit index. Broad scopes can reuse generation-stamped live/profile masks; selective scopes should drive postings intersections. An arbitrary historical range needs more than last-visit metadata. Neither that general scope builder nor distinct-group top-k was measured.
5. **Retain recency ties.** Equal-score blocks cannot be skipped merely because their BM25 bound equals the heap minimum. Start with the measured exact traversal when needed. Only add early termination with proven bounds for the complete score/tie tuple, or a separately approved tie policy. A newer-first physical document layout could help but was not measured. Default Tantivy BM25 statistics include segment documents awaiting merge, including deleted ones; pin the scoring generation and decide whether live-only statistics are needed before claiming rebuild-stable scores. See [the statistics implementation](https://raw.githubusercontent.com/quickwit-oss/tantivy/0.26.2/src/query/bm25.rs).
6. **Separate page ranking and counts.** Return a verified top page without waiting for exact counting. Count matching URL groups using no-score postings/bitmaps; compute matching-visit totals separately. Cache by complete generation/filter/query identity. Never treat raw posting frequency or child-document count as the page total. More expensive counts can report monotonic progress until exact.
7. **Own updates in `search_projection.rs`.** Reuse its affected-URL projection boundary for backups, imports, reverts/restores, notes/tags and enrichment changes. Record a durable canonical change generation/outbox in the same transaction as canonical facts, then replace affected lexical records and eligibility state. Publish an index commit only with the matching watermark. A crash before publication leaves a replayable delta; an incompatible/corrupt sidecar is rebuilt. Reverted data must never leak while the index catches up: use canonical validation/visibility overlays or the complete canonical fallback. Do not label stale index results as complete coverage.
8. **Pin pagination to a generation.** Cursor includes query/filter hash, scoring/analyzer version, generation and stable score/tie/group position. Hold a reader snapshot or explicitly restart after invalidation; merges change document addresses. The prototype only tests first/second pages. Deep paging needs a tested continuation collector or an encrypted external result spool; a growing top-k/offset is not a scalable millionth-page design. Every match remains enumerable, including exports; no 25,000 ceiling.

For existing users, preview the build, disk requirement and fallback behavior, then let the user start a cancellable backend job. Build alongside the old index, report progress and switch atomically only after count/visibility checks. The measured **38.14 s / 334.8 MiB** covers the reduced engine build and merge on this host, not canonical reads plus the full product projection. Budget old and new generations plus merge scratch; the experiment alone briefly needed both the 364.6 MiB unmerged and 334.8 MiB merged files. Encrypted users must build directly to encrypted storage, whose cost is still unknown. Migration/rekey publication must coordinate both encrypted-tier databases and the derived generation; invalidate sessions/caches on lock and key changes. The existing plaintext sidecar is a documented exception under `WORK-ENCRYPT-AT-REST-ALL`, not evidence that new sensitive indexes may silently ignore encryption.

The UI remains backend-driven through the typed client: immediate skeleton, cancellable search ID, final globally ranked pages when certified, and an independent count-progress response. During build/catch-up, expose index progress and the complete fallback search rather than hiding older results. If results are provisional while shards/spools are still being processed, say so; do not repeatedly reorder a list presented as final. Any eventual new copy must ship in en/zh-CN/zh-TW. No frontend implementation is part of this research.
