# Turso evaluation: research report (2026-10-04)

> Measured by Codex (GPT 6 astra) for [large-result-search-tradeoff.md](../large-result-search-tradeoff.md). Links to `results/`, `src/` and other prototype files point to the research checkout, which was not kept.

Stay with SQLite/SQLCipher for PathKeep’s databases. Turso offers much faster index-only top-k search, but that benefit does not require converting the canonical archive, source evidence, intelligence store, and chat store. The full grouped search still processes the matching visits, while an all-store switch would require new key management, encrypted export/recovery code, a Rust API adapter, and a search-language port. Those costs outweigh the measured benefits of a wholesale replacement. Both engines can encrypt all five database files; neither automatically protects PathKeep’s non-database artifacts. Continue the separate search investigation before choosing a new search backend.

**Scope and evidence.** This evaluates the local Rust database engine, not the Turso cloud service or the older libSQL engine. Version **0.8.1**, released 2026-09-29, was the current stable release on 2026-10-04; crates.io also offered `0.8.2-pre.2`. Cargo pins `turso = 0.8.1` and PathKeep’s `rusqlite = 0.39.0` (bundled SQLCipher 4.10.0, SQLite 3.50.4), with a retained lockfile. Upstream references below are pinned to `v0.8.1`, commit `8549c16595d2faf1bdd6ee24aee0be8bfabb3d4a`. Product code was inspected at `60d2b8097df5474bde8a733406ec1c1670e10cd9`. No product files, plans, or accepted decisions were changed. [Release][release]; [recorded metadata](release-metadata.json).

**Verified inventory and capability map.** PathKeep has **five** principal database files, not four. `archive/source-evidence.sqlite` is canonical, encrypted alongside `archive/history-vault.sqlite`, and included in portable bundles. The other three are `derived/history-search.sqlite`, `derived/history-intelligence.sqlite`, and `derived/agent.sqlite`. Search attaches plaintext with `KEY ''`; intelligence attaches the keyed archive; agent is independent. Browser originals, staged snapshots, and import staging add SQLite consumers outside those five. [Paths](../../src-tauri/crates/vault-core/src/config.rs); [at-rest contract](../../docs/architecture/data-model.md); [staging](../../src-tauri/crates/vault-core/src/chrome/staging.rs).

**Encryption findings.** Native Turso encrypts individual database and WAL pages, not an opaque whole-file container. The implementation offers AES-128-GCM, AES-256-GCM and several AEGIS variants. The benchmark uses **AEGIS-256**, a 32-byte raw key, a fresh 32-byte nonce and a 16-byte authentication tag per page. The first 100 bytes of page 1 remain clear and are authenticated as associated data; the SQLite signature is replaced with Turso/version/cipher bytes. File length, page geometry, change/schema counters and other header metadata therefore remain observable. Page contents, schema text and FTS index bytes are encrypted. WAL framing and `.tshm` coordination metadata are separate from encrypted page payloads. In-memory pages are plaintext. Key material has a wiping Drop implementation; this is not a claim that every string or cached page is wiped. [Encryption implementation][crypto]; [WAL][wal].

SQLCipher instead derives keys from a password using salted PBKDF2-HMAC-SHA512 (256,000 iterations by default), and protects pages with AES-256-CBC plus HMAC-SHA512. It can also accept raw keys. Turso’s raw-key open timings therefore are **not** password-unlock comparisons. An application KDF and salt/version metadata would add their own unlock cost. [SQLCipher design][sqlcipherdesign]; [Turso key parser][crypto].

Every one of PathKeep’s five DB files could use native encryption. The FTS implementation stores Tantivy segment bytes in database backing storage, so it does not require a plaintext Tantivy directory beside an encrypted search DB. The benchmark created and queried encrypted archive and search files, attached them, and exercised an independent writer process. The small wrong-key probe failed; the correct key succeeded. Intelligence and agent schemas were inspected, not fully ported. [FTS directory and storage boundary][ftsdirectory]; [capability evidence](capabilities.jsonl).

This **does not close WORK-ENCRYPT-AT-REST-ALL by itself**. Vector planes, fetched-content blobs, browser snapshots and other non-database artifacts need their own scope decisions and protection. Turso’s temporary spill files are opened through ordinary I/O without the database page codec; inspect that path before allowing sensitive sorts to spill. `temp_store=MEMORY` alone is not a satisfactory answer for unbounded work on an 8 GB machine. SQLCipher’s documentation also excludes some transient files unless file-based temp storage is disabled, so PathKeep’s export `temp_store=FILE` deserves examination whichever engine wins. [PathKeep at-rest contract](../../docs/architecture/data-model.md); [Turso temp files][io]; [SQLCipher transient files][sqlcipherdesign].

The executable export probe matters: `VACUUM INTO` produced a normal SQLite header and a sentinel string readable by rusqlite without a key. Its implementation opens the target with no native encryption options. Explicitly attaching a new destination with `cipher`/`hexkey`, creating a table there and copying rows **did** produce an encrypted file. An encrypted bundle must use that explicit path, copy the complete schema/data contract, checkpoint and close outputs, verify them with the destination keys, then build the existing manifest/ZIP. It must not use a plaintext intermediate. PathKeep’s current bundle is a ZIP with separate manifest/config and other eligible artifacts, not an encrypted outer container. Encrypting its DB entries does not conceal ZIP metadata or protect other plaintext entries; a whole-bundle encryption promise would need a separate container format decision. [Bundle writer](../../src-tauri/crates/vault-core/src/migration.rs). A native page-key rotation needs the same rewrite. A future envelope-key design could make password changes rewrap a random data key, but that is a new application security contract, not a native `rekey` feature. [VACUUM implementation][execute]; [measured probe](capabilities.jsonl).

**Search findings.** Turso really changes the ranking algorithm available through SQL. Its limited, descending-score pattern calls Tantivy’s `TopDocs`; term and Boolean queries can use pruning instead of computing and sorting every match’s BM25 score. The 1M and 14.4M measurements below test both that narrow query and a separate grouped query that reads the full matching set and computes visible visit counts/latest visits. Exact counts still traverse matches; they do not acquire a sublinear guarantee from top-k. [Native query patterns][fts]; [Tantivy pruning][termweight]; [Tantivy Boolean scoring][booleanweight].

PathKeep’s reported **10.5 seconds** was a grouped product search over 3.6M URL documents at 14.4M visits, including its term/trigram combination and visibility joins. Comparing that number directly to a bare native top-k query would be misleading. This prototype ports the main grouping and visit-index shape but specializes away unused filters and the duplicate-URL window; it also uses term-only searches for an equal match set. Current checkout code contains a 25,000-URL window that STATUS says the owner rejected. This experiment never applies that cap: all indexed documents remain eligible, and the grouped query sees all visible matches. [Current grouping](../../src-tauri/crates/vault-core/src/archive/history/grouped.rs); [status](../../docs/plan/STATUS.md); [prior measurement](../../docs/architecture/ipc-performance.md).

At 14.4M, the plaintext warm index-only `topic` page was **2.31 ms native versus 871.53 ms FTS5**. The grouped visible-page query was **6.38 s versus 6.76 s**. Those observations support a ranking-engine improvement, not an automatic fix for the whole History query. Score-only top-k also leaves PathKeep’s newest-visit/URL tie ordering unresolved; adding an ORDER BY expression can change whether the native planner pushes the limit into its FTS collector.

A future native top-k integration would have to push filterable facts into the search document or iteratively retrieve and validate candidates until it proves the requested page is correct. Taking 101 global hits and then filtering hidden visits can silently omit valid results. Keeping SQLCipher for canonical facts and using an encrypted native search DB would also remove the current cross-engine ATTACH path: candidate IDs and hydration would cross an application boundary. These are search architecture costs, not reasons to migrate every store.

The row-at-a-time FTS pilot was stopped after 243.7 seconds for its complete partial run; archive import/export had finished, but its 250,000-document projection had not. A separate reader observed only 25,000 committed documents during that run. The source explains this: pending FTS documents flush into a segment at **statement end**, even inside a larger transaction. Bulk-loading documents first and creating the native indexes afterwards brought projection construction to the measured times below. Ongoing ingest therefore needs multi-row statements or `INSERT … SELECT`, not a mechanical copy of PathKeep’s prepared one-row projection writes. The earlier timings are preserved separately and excluded from the comparison. [Flush contract][fts]; [pilot artifacts](pilot-results/).

Both native 14.4M producer processes stopped advancing after index construction: plaintext at the next ATTACH, encrypted at the first search. A separate process could read the completed database. The producers were interrupted; their completed archive/import/export/index timings were retained, and all search measurements were completed against the same files in fresh processes. The plaintext read phase attached in **172 ms**; final fresh-process checkpoints took **398 ms plaintext / 898 ms encrypted** and removed the remaining WALs. The cause was not diagnosed, and closing one handle alone was not established as a fix. A PathKeep integration must resolve this build-to-read lifecycle before using the measured search path. This is a specific prototype observation, not a general engine stability assessment. [Plaintext interrupted run](attach-pilot-results/); [encrypted interrupted run](post-build-pilot-results/); [plaintext resumed queries](resumed-search-14m.jsonl); [encrypted resumed queries](resumed-encrypted-search-14m.jsonl).

The retained harness now separates native build and read processes. That automated orchestration was smoke-tested at 1,000 visits; the full-size measurements used the manually interrupted producers and completed fresh readers described above. They were not rerun as a new uninterrupted end-to-end pipeline. Operation timings exclude the stalls and pause between phases; raw phase exit codes preserve what happened.

**Performance method.** The retained Cargo project uses the scale generator’s exact LCG seed/multiplier, skewed URL choice, three profile assignments, 20,000 domains, one URL per four visits, and five-year monotonic visit timestamps. The essential schema preserves the relevant archive columns, FKs, AUTOINCREMENT and time/URL/profile read indexes. It omits production source-ID deduplication, import-batch, URL-last-visit and registrable-domain indexes, as well as unused tables/columns. Consequently import times, conversion times and file sizes are **not full-product archive measurements**; the comparison is between engines on the same reduced schema. Archive imports commit/checkpoint in 25,000-row batches in both engines to bound WAL space; the source fixture used one large transaction. Timings include data generation and index maintenance, but exclude search projection, which is shown separately. Both engines use WAL, synchronous FULL, a requested 64 MiB cache on explicitly opened connections, and file-backed temp storage. Attached database cache sharing/defaults are engine-specific and were not normalized. No mmap was explicitly enabled. This is a storage/query prototype, **not the complete application or its browser-ingest pipeline**.

Search construction includes the ten-field term index and the compact-text index (native default 2–3-grams, SQLite trigrams). The ASCII synthetic corpus does not exercise ICU/OpenCC/CJK normalization or populated notes/enrichment. For a valid equal-match comparison, `topic 42` means the **exact tokens** `topic AND 42` in both engines; it does not include PathKeep’s prefix/trigram union. The rare query is `page AND 83334` at 1M and `page AND 1200001` at 14.4M. Plain document counts and visible grouped counts are separate. The completed query samples contain no query errors, and both engines’ counts are checked against each other in [validation.json](validation.json).

History pages fetch 101 rows, newest-first. Export streams the same nine selected fields into real JSONL using a 256 KiB buffer, flushes and fsyncs, validates descending IDs/count/sum, then deletes the output. It is not a `.pathkeep-bundle` export and does not claim the full product JSON shape. Export bytes/checksums match across engines. Queries run 3 times (history and concurrent reads 5); tables report medians. Import/projection/export run once per variant. Page, count, search and export timings reuse already-open connections: they exclude connection creation, SQLCipher password derivation and attachment setup. These are warm-process tests, not controlled cold-cache tests. The concurrency test starts a **second OS process**, updates 1,000 visits, holds its transaction for one second, and serves five history pages from the parent while the transaction is open.

Hardware is the shared Apple Silicon Mac described in the repository benchmark notes (18 cores, 64 GB, SSD), not the 4-core/8 GB target. Hardware sysctl/process-RSS inspection was denied by this session’s sandbox, so that specification is inherited from those notes, not independently measured. Rust was 1.96.0. Other jobs ran throughout; a few probe builds and temporary-cache cleanup also overlapped measurements. Every timed sample records literal `uptime`; the tables include loads, and raw logs retain all three load averages per sample. Load movement makes small apparent encryption speedups noise, not an engine guarantee.

<!-- END_ENCRYPTION_COSTS -->

Native encrypted runs encrypt **both archive and search**. “SQLCipher current” encrypts the archive but leaves search plaintext, matching PathKeep today. “SQLCipher all” encrypts both and is an additional 1M control: the existing engine can encrypt the search projection without changing FTS. The two engines use different cipher constructions; these are their selected configurations, not equal-cipher crypto-library benchmarks. The timings do not measure a password KDF for Turso, AES-GCM, long-term random-write workloads, or the encryption of intelligence/agent/vector/blob data.

**Migration cost, if reconsidered.** No migration is recommended or started. A viable future implementation would keep SQLCipher available to read old encrypted archives; Turso’s native header/cipher format is different. The compatibility probe opened an existing plaintext SQLite table/index file through Turso, but rejected an existing SQLCipher-encrypted file. For plaintext ordinary-table SQLite files, format compatibility can avoid a row conversion only after validating the exact schema and extensions. It cannot preserve SQLCipher ciphertext or reuse an FTS5 index as native Tantivy FTS. [Compatibility probe](capabilities.jsonl); [Turso file header][crypto]; [Turso README][readme]; [FTS implementation][fts].

For encrypted users, add a reviewable engine-conversion preview (disk/time estimate, affected files, recovery behavior) and manual start, then use the existing “Upgrading your archive” progress surface before making the archive available. Progress/cancellation and all visible copy would follow the existing typed IPC and three-language contracts. Acquire an application-wide lock that both desktop and worker honor; stop writers; check password and free space; create sibling encrypted destination files; copy immutable canonical IDs and all schema/data; rebuild derived search; validate counts, foreign keys, content digests and reopen with the target keys. Version the storage engine, cipher and application KDF in configuration and portable-bundle metadata; an archive SQL schema version alone cannot tell an older binary how to read a new encryption format. Only then commit a durable conversion manifest and swap the coordinated files. Preserve the old encrypted set until the new set has been verified. Record per-table/chunk progress with a fixed source snapshot, so interruption either resumes that version or discards the incomplete new files and leaves the old engine usable. A rename of one file is not a transaction across five files. Reuse the existing interrupted-rewrite journal patterns rather than relying on in-memory flags. [Existing at-rest recovery](../../src-tauri/crates/vault-core/src/archive/at_rest.rs); [upgrade surface](../../src-tauri/crates/vault-core/src/archive/schema.rs).

That measurement copies only the prototype’s URLs/visits and indexes into a new native encrypted database through bounded row streaming. It is not a duration estimate for a real user’s source evidence, BLOBs, annotations, full audit schema, derived rebuild and validation. Budget disk for old encrypted canonical files plus new encrypted canonical files, peak WAL/temp work, and rebuilt projections; do not keep a plaintext backup as the restart mechanism. Real large-BLOB archives may need substantially more room than this fixture.

The code search found **127 Rust files** mentioning rusqlite, **105 outside test paths**, with 444 textual mentions. Those files total 109,690 lines; that is a scope indicator, not a proposed diff size. The high-level native Rust API is async for build/prepare/execute/query/next, uses different params/rows/errors and transaction behavior, and omits some hooks used here. It is not a near drop-in. A lower-level synchronous core adapter can keep a blocking worker architecture, but then PathKeep owns its row/transaction/cancellation/I/O abstractions. [File inventory](rusqlite-files.txt); [public Rust API][api]; [connection methods][rustconnection].

Planning estimate, not a measured implementation: **80–120 production files and 5,000–12,000 changed lines**, plus fixtures/E2E, for an all-store conversion with a deliberate adapter. Allow approximately **12–24 engineer-weeks** across adapter/query ports, encryption and bundle/recovery work, search parity and three-platform validation. A direct async propagation strategy can exceed that range. Browser-original readers and SQLite online snapshot capture should remain on rusqlite, so switching all owned stores still does not necessarily remove SQLite/SQLCipher from the binary. This task does not estimate a Tantivy-only implementation; that belongs to the separate search study.

**Build and supply chain.** The Turso repository is MIT-licensed, maintained under the `tursodatabase` organization, and had **24,595 stars** when recorded. It exceeds the repository’s 6,000-star dependency threshold. This is a license/ownership/dependency observation, not a maturity argument. [License][license]; [repository metadata](release-metadata.json).

The native engine avoids SQLCipher/OpenSSL but the evaluated Rust package is not a pure-Rust build: default mimalloc, Tantivy’s Zstd dependency and default SIMD code compile bundled C. The SDK enables pure-Rust cryptography; core also selects it on macOS/Android. Cargo does not require installing a database or crypto package with Homebrew/apt/winget for this configuration. Platform toolchains are still required; the Windows SDK-kit build invokes its resource compiler. On this Mac, `otool -L` showed only OS libraries/frameworks for both minimal binaries, not a dynamically linked Homebrew OpenSSL/Zstd/SQLite. [Rust manifest][rustcargo]; [core manifest][corecargo]; [SDK manifest][sdkcargo]; [Windows build script][sdkbuild]; [linked libraries](linked-libraries.txt).

Measured stripped release binaries for tiny in-memory SQL/FTS programs were **5,949,360 bytes** for rusqlite/SQLCipher and **22,834,576 bytes** for Turso, about **16.1 MiB larger**. This is a library integration comparison, not a prediction of the Tauri application bundle delta; retaining SQLite for browser capture makes the engines additive, while shared dependencies can reduce duplication. [Programs](src/bin/); [measurements](build-size.json).

A clean target build of the combined dependency graph took **128.37 seconds** (389.89 CPU user seconds, four Cargo jobs), with the Cargo package cache available; the initial stub linked no workload. Subsequent prototype compilation took about 11 seconds. This is **not** a separate clean-build comparison between engines, so no claim that switching improves or worsens application compile time is justified. The dependency graph adds substantial native-engine/FTS Rust compilation while removing OpenSSL only if no remaining component needs it. [Build log](build.log); [lockfile](Cargo.lock).

**Risks and unmeasured work.** The main unresolved fit issues are full search semantics (single-term prefix, trigram/CJK/diacritics, weighted union, filters, grouping and pagination), cancellation before first row through the chosen Rust adapter, encrypted temp/export behavior, and coordinated key/conversion recovery. All are independent of whether Turso is considered mature. No full intelligence or agent-store workload, giant BLOB/evidence archive, browser-live WAL handoff, crash/power-loss campaign, platform installer, target-hardware memory profile, long-running mixed read/write throughput, cold-start FTS hydration, or adversarial cryptographic audit was performed. The resident segment-cache design and full matching-set grouping deserve measurement on 8 GB hardware. [FTS cache/directory implementation][ftsdirectory].

The benchmark’s exact-token searches and reduced grouping cannot prove feature parity with PathKeep’s complete keyword language. Nor does a successful single writer/reader exercise prove every desktop/worker race. Product `bun run check` was not run because product code was unchanged; validation here consists of release compilation, actual engine probes, repeated query measurements, export invariants and result-count comparisons.

**Reproduction and cleanup.** Run from the repository root with a writable Cargo home and sufficient disk space:

```sh
CARGO_TARGET_DIR=research/turso-eval/target CARGO_BUILD_JOBS=4 \
  cargo build --release --locked --manifest-path research/turso-eval/Cargo.toml --bins
python3 research/turso-eval/run.py 1000000 14400000
python3 research/turso-eval/summarize.py
python3 research/turso-eval/validate.py
python3 research/turso-eval/render_tables.py
```

The runner processes one variant at a time, checks an 11 GiB data guard once per second, records every timing/load, and deletes the data directory after each run, including failed runs. Native variants run build, fresh-reader and checkpoint phases separately. It skips variants with existing summary files; move `results/` aside for a fresh repeat. Its 14.4M SQLCipher encrypted run also executes the conversion prototype before deleting that run’s files. The project source, Cargo lockfile and textual evidence remain. All generated databases, exports, native-engine checkout, temporary Cargo cache and target directories created by this task are removed before delivery.

Cleanup verified: **9 measured variants**, largest observed benchmark-directory footprint **8.326 GB**, no generated databases/exports or created target/cache directories left. See [cleanup.json](cleanup.json) and [validation.json](validation.json).
