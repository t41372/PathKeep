## 新查找快取失敗的現有因果線索

自訂量測中，14.4M 造訪映射已載入；向量查找表提交 4,990,976 筆後，下一批寫入中止。診斷記錄的失敗頁為 262145，恰是 4096-byte page 的 1 GiB 特殊保留頁。

本機 Turso 0.8.3 的 `AllocateNewPage` 路徑配置這一頁後直接標 dirty，註解假設其已清零；它未走一般 B-tree 頁的初始化。這與失敗位置一致，但仍只構成這份非標準量測的候選根因。正常 app 能否到達、哪些資料庫會受影響、是否還有上層原因，未完成正式流程複核。

使用者已明確拒絕修改依賴。不得套用 vendor patch、改 registry source、關閉斷言或以降低資料量放行。也不得為迴避這個可疑項，直接把現有架構換成另一套未確認方案。

## 接下來的順序

1. 停止擴大修復範圍，保留目前修改供審查，不宣稱完成。
2. 對照原始 app、既有紀錄與產品入口，完成原始計數／續跑／映射問題的因果鏈；列明已排除及未排除的解釋。
3. 對可疑項先寫正常使用流程的重現步驟與應觀察的狀態。不得用故障注入、直接改內部資料或自訂 benchmark 取代正常流程證據。
4. 只有在問題成立且根因確認後，才比較修法的正確性、14.4M 資料成本、維護性與既有契約，寫定方案，再修改程式。
5. 全部必要修復完成後，才執行整體測試與 `bun run check`。若有新失敗，先調查及規劃，不直接修。
6. 完整驗證通過後才提交；不修改依賴碼，不聯絡上游。

## 正常入口複核的第一個差異

正式整庫還原入口是 `vault-worker/src/archive_flows.rs::run_full_archive_restore`。它在安裝後呼叫 `maintenance::record_restore` 保存 review run；先前撞名重現直接呼叫 core 還原 API，沒有這一步，還特意保留舊 lease。因此該重現的 run id 時序不能直接代表 UI 流程，也不能據此宣布命名修法已確認必要。

後續必須先核對 UI 可到達的快照建立／選取／還原步驟、正式入口的額外 run，以及 reader 關閉與 GC 順序。若正常流程不會形成相同狀態，應排除此問題或縮小其適用範圍，而非修改正常流程去配合重現。

映射更新的正常重現應使用實際瀏覽器寫入 History、正常備份與索引操作；不得再直接改 SQLite 的 title／last_visit_time。可用同一頁面先後兩次正常造訪、頁面標題確實改變的情境，觀察舊／新造訪目前的相同文件身份是否得到相同 key。讀取已產生的映射只作證據，不修改它。enrichment 的重現則必須經正式抓取／發布入口，不能直接寫入內部表。

每項紀錄均須包含：起始版本與設定、正常操作順序、觀察結果、預期結果、可能的其他解釋、排除證據，以及方案與替代方案。尚未取得正常流程證據的項目，狀態持續為可疑。
