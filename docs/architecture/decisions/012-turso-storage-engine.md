# ADR-012 — 關聯式資料改用 Turso，搜尋改用 Tantivy 索引

## 狀態

Accepted（2026-10-05）。用戶在記憶體量測後選定：關聯式資料用 Turso，全文搜尋用獨立的 Tantivy 索引，不用 Turso 原生 FTS。

驗收結果見文末。和最初的設想相比，有三點改了：

- 大量寫入不用 MVCC；
- 只有一個行程擁有資料庫；
- **全文搜尋不用 Turso FTS**，原因有三：
  - 它把整個索引常駐在記憶體，搜尋一用就約 600 MB；
  - 備份更新 100 萬頁時，峰值 2.9–3.4 GB，公開介面也沒有任何可調的記憶體設定；
  - 常見詞排序比 Tantivy 自訂 collector 慢（262 ms 對 55 ms）。

取代 [large-result-search-tradeoff.md](../large-result-search-tradeoff.md) 的建議。那份文檔把遷移成本和工作量當成取捨理由，還提了過渡方案，違反核心原則 6。

## 背景

- **搜尋必須覆蓋整個 archive**（用戶 2026-10-04 決定）。搜不出來的記錄，對用戶來說就是不存在。
- **常見詞的相關度排序太慢。** SQLite FTS5 會替每個符合項打分：在 14.4M 筆訪問上，「topic」第一頁 10.5 秒，精確計數 26.6 秒。過去為了繞過這個問題，做了窗口、由新到舊的退路、符合集合快取、分段計數，每一項都是 workaround，窗口甚至讓結果搜不到。
- **加密 archive 很慢。** SQLCipher 讀每一頁都要解密：按頁面分組的查詢明文 6.8 秒，加密 26.8 秒；全量匯出 30 秒對 84 秒。
- **at-rest 保護不完整。** 搜尋、intelligence、AI 對話三個資料庫是明文（data-model.md 記載的例外，backlog `WORK-ENCRYPT-AT-REST-ALL`）。
- **備份時 app 用不了。** 調查結論：原因不在 SQLite 的讀取（WAL 下讀不會被擋），在 PathKeep 自己：
  1. 備份後重建整個搜尋索引；
  2. 讀取路徑在首次備份時會自己去重建索引；
  3. 冷啟動用 `BEGIN IMMEDIATE` 做 schema bootstrap；
  4. 前端讀取失敗後不會重試；
  5. 單一寫入者：備份的長交易進行時，加星、筆記、標籤等使用者寫入要等 5 秒，然後失敗。

## 決策

PathKeep 自己的五個資料庫（archive、source evidence、search、intelligence、agent）全部改用 Turso。

1. **全部加密。**
   - 關聯式資料用 Turso 原生加密（按頁）。
   - Tantivy 索引用我們自己的加密 Directory：認證的 AES-256-GCM 區塊、有上限的解密快取、寫入和合併都直接寫密文、崩潰可恢復。
   - 不再有明文的衍生資料。
2. **金鑰管理。**
   - 應用程式用 Argon2id 從密碼推導出 key-encryption key，用它包裝一把隨機的 256-bit data key，所有資料庫都用這把 data key 開啟。
   - 改密碼只需要重新包裝 data key，資料檔不用重寫。
   - 驗收用的參數：Argon2id m=256 MiB、t=3、p=4，包裝用 AES-256-GCM，94 bytes 的信封會認證 KDF 參數。在 18 核開發機上解鎖 297 ms；目標機要重新量。
3. **全文搜尋用獨立的 Tantivy 索引。**
   - 每個頁面（以 URL 字串為單位，跨瀏覽器合併）一份搜尋文件。
   - **同步：**
     - 資料變動時，在同一個 Turso 交易裡寫一筆 outbox。
     - 擁有者行程裡的索引執行緒消化 outbox，更新 Tantivy，並把已處理到的位置存進索引的 commit。
     - 崩潰後從那個位置重放。索引不見、損毀或版本不符時，從 canonical 資料重建。
   - **可見性：** 搜尋結果一律以 Turso 的 canonical 資料為準（eligibility 從 SQL 算），所以索引追趕期間不會顯示已撤銷的資料。
   - **排序：** 用 Tantivy 自訂 collector，先相關度，再最新可見訪問，最後頁面 id。篩選盡量推進查詢本身。前綴、片語、排除用 Tantivy 的查詢物件直接組，不經文字解析。
   - **計數：** 和排序分開算，精確。
   - **記憶體可以設上限：** 寫入堆積大小、解密快取大小、reader 的重新載入策略。
   - **不再有：** 窗口、由新到舊的退路、符合集合快取、「準備中」階段、分段計數，也不再在備份後重建整個索引。
   - **呈現上仍然分段串流**（用戶 2026-10-04 要求）：在配置差的機器上，也要先回第一批結果，更多結果和計數陸續到，任何時候畫面上都看得到進展。
4. **Regex 照舊分段掃描並串流顯示。** Regex 用不了索引，掃 14.4M 筆一定需要時間；串流呈現是對的設計，不是 workaround。
5. **只有一個行程擁有資料庫，用 WAL，不用 MVCC。**
   - 多行程 WAL 有 `.tshm` frame 索引上限（262,144）：大交易後，讀取會卡 10 秒以上。單一行程模式用的是另一套 WAL 協調機制，沒有這個上限，已實測 309,333 frames。
   - 排程備份和 MCP 不再自己開資料庫檔，一律經由擁有資料庫的行程。
   - MVCC 的並行本身正確，但它把未提交的交易全放在記憶體裡：100 萬筆的交易峰值 10 GB，暫存寫入慢 3.4 倍，提交要 25 秒，checkpoint 要 55 秒。所以不用在備份和匯入上。
6. **備份和匯入分批提交，使用者的寫入插在批次之間。**
   - 這是「備份時加星、筆記照樣能存」的做法，靠我們的架構，不靠引擎。
   - 一次備份不再是單一個原子交易，所以 run 模型要定義「部分完成」的可見性和恢復方式。
   - 批次大小用記憶體量測決定。
7. **每個資料庫連線只由一個執行緒擁有**，同步的 request/reply 介面接上 Tauri 的 blocking 執行緒池。查詢取消改成合作式：每批之間檢查，0.36 ms 就停，因為 Rust 介面沒有公開中斷正在執行的查詢。
8. **讀瀏覽器原始檔仍用 rusqlite。**
   - Chrome、Firefox、Safari 的歷史是瀏覽器自己的明文 SQLite 檔，常常正在使用中。用 SQLite 的 online backup API 拿快照，再寫進 Turso。
   - 只需要一般的 bundled SQLite，不再需要 SQLCipher 和 vendored OpenSSL。
   - Turso 對正在使用中的 SQLite 檔拿快照不安全：SQLite 回收 WAL 後，Turso 會讀到不完整的 frame。兩個引擎可以共存在同一個執行檔（stripped 21.5 MiB）。
9. **永遠不用 `VACUUM INTO` 複製加密資料庫**，它輸出的是明文。搬家用的匯出包，用明確 ATTACH 一個加密的目的資料庫再完整複製；Turso 內部的 FTS 表不能複製，要在目的地重建索引。
10. **暫存和溢出檔要加密。**
    - Turso 把排序、分組、hash join、建索引的溢出檔以明文寫進系統暫存目錄。
    - 我們用 `with_io_impl` 提供一層 IO，用只存在記憶體裡的金鑰（AES-256-CTR）加密暫存檔。
    - 不用 TEMP 表，改用 ATTACH 一個加密的 scratch 資料庫。
    - 這依賴 Turso 內部的暫存檔名（`tursodb_temp_file`），每次升級 Turso 都要重跑溢出測試。
    - Apple Silicon 要開 `--cfg aes_armv8`，不然 AES 走軟體實作，慢約 7 倍。
11. **匯出查詢要寫成不排序的形狀**（例如 `CROSS JOIN`），並用測試確認查詢計畫裡沒有 sorter，免得把整份資料溢出到磁碟。
12. **和引擎無關、也要一起修的問題：**

- 冷啟動不能用 `BEGIN IMMEDIATE` 擋住所有讀取；
- 讀取路徑永遠不重建索引；
- 前端遇到暫時性的忙碌錯誤，要能自己恢復，不能停在錯誤畫面。

## 驗收條件（全部要有可執行的測試，結果記在 RESULTS.md）

1. **全文查詢語法與現在一致。** 包括單一詞的前綴（`topi*`、`42*`）、邊打邊搜（最後一個詞是前綴）、片語、排除、十個欄位的權重、ngram 的錯字容忍和中文。
2. **在 14.4M、加密的情況下，帶篩選、每個頁面一行的相關度 top-k 正確**（和窮舉計算比對），計數精確，延遲可接受。
3. **MVCC 能和加密、FTS、ATTACH、多行程同時運作。** 備份的長交易進行時，小寫入不必等它，讀取不受影響，FTS 保持一致，不卡死。
4. **找出之前原型裡「建完索引後行程停住」的根本原因**，並修掉或繞開。
5. **加密設計可行。**
   - 金鑰包裝；
   - 加密複製（輸出確認是密文）；
   - 暫存或溢出檔不寫明文；
   - kill -9 之後能恢復，完整性檢查通過。
6. **Rust 介面能做到現在依賴的事。** 跨執行緒中斷查詢（匯出取消）、`RETURNING`、忙碌處理。
7. **rusqlite（讀瀏覽器）和 Turso 能共存在同一個執行檔裡。**
8. **貼近產品工作負載的記憶體能放進 8 GB 的機器**（和作業系統、webview 一起），包括搜尋、分批備份、全量匯出、一次匯入 14.4M。

## 驗收結果（2026-10-05）

| #   | 條件                 | 結果                                                                                                                                                                                           |
| --- | -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 全文查詢語法         | Turso FTS 通過，需繞過（前綴）。改用 Tantivy 後，查詢物件直接組，不受此影響。                                                                                                                  |
| 2   | 14.4M 帶篩選的 top-k | Turso FTS 通過，需繞過（Rust collector，「topic」熱的 262 ms）。改用 Tantivy 自訂 collector（研究實測 55 ms），重新驗收。                                                                      |
| 3   | MVCC 加多行程        | **不通過。** MVCC 不支援多行程；單一行程裡並行正確，但大交易的記憶體不可接受。改走決策 5、6：單一擁有者、WAL、分批。                                                                           |
| 4   | 建完索引後停住       | 多行程 WAL 的 `.tshm` 上限所致；**單一行程模式下不會發生**（決策 5）。                                                                                                                         |
| 5   | 加密                 | **通過**（溢出檔和匯出包需繞過，見決策 9、10）。kill -9 共 162 次，0 次失敗。                                                                                                                  |
| 6   | Rust 介面            | **不通過**：沒有中斷正在執行的查詢的介面。改用合作式取消（決策 7）。`RETURNING`、忙碌處理通過。                                                                                                |
| 7   | 兩個引擎共存         | **通過。**                                                                                                                                                                                     |
| 8   | 記憶體               | **Turso FTS 不通過。** 備份更新 100 萬頁時峰值 2.9–3.4 GB，沒有可調設定。關聯式部分通過：全量匯出 24 MB，第一次匯入 14.4M 1.2 GB（含建索引）。所以改成 Turso 關聯式加 Tantivy 索引（決策 3）。 |

## 後果

- 搜尋的覆蓋率和加密由引擎解決。「備份時照常讀寫」由我們的架構解決，也就是單一擁有者加上分批提交；這在任何引擎上都需要。
- 要我們自己維護、並在每次升級 Turso 時重驗的部分：
  - Tantivy 加密 Directory 和同步 outbox；
  - top-k collector；
  - 暫存檔加密 IO；
  - 匯出包的索引重建。
- 要刪掉的代碼：
  - 窗口、由新到舊退路、符合集合快取、分段計數；
  - 明文搜尋資料庫的 `ATTACH … KEY ''`；
  - 備份後的整個索引重建。
- 現有的 SQLCipher archive 要轉換。現在幾乎沒有真實用戶，轉換流程照現有的「升級 archive」畫面做（預覽、可取消、有進度、驗證後再切換），不為舊格式長期保留相容層。
- 執行檔裡會同時有 Turso 和一般的 SQLite（只用來讀瀏覽器）。
- Turso 的加密、FTS、多行程在 0.8.1 標為 experimental（本設計不用多行程）。按用戶要求不以成熟度做取捨；靠上面的驗收測試和 E2E 守住行為。
