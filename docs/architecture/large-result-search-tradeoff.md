## 1. 問題

用戶 2026-10-04 定下的要求：**搜尋一律覆蓋整個 archive**。搜不出來的記錄，對用戶來說就是不存在，等於資料遺失。慢的話在呈現上解決：分段、結果 stream 回來，不能讓用戶乾等。

所以 25,000 頁的窗口（`8554fb6a`）不能留。可是一個常見詞，在 14.4M 筆訪問的 archive 裡有兩筆貴的工作：

1. **按相關度排序。** FTS5 的 bm25 會替每個符合項打分。「topic」符合 360 萬份文件，取前 100 名時，排序函數被呼叫了 3,600,000 次。FTS5 沒有剪枝，調參調到極限也要約 1.1 秒。
2. **按頁面分組並套用可見性與篩選。** 每個符合的頁面都要算可見訪問數、最新訪問時間，日期和瀏覽器篩選也要落在同一筆訪問上。這一步和排序引擎無關：
   - 明文 SQLite 6.8 秒，Turso 6.4 秒；
   - **加密 archive（大多數用戶）26.8 秒**，因為 SQLCipher 讀每一頁都要解密。

只解決第 1 項不夠。第 2 項需要把分組和篩選需要的資料放進搜尋索引，或者另建專門的結構。

## 3. Turso 為什麼不建議全換

Turso 評估的結論是留在 SQLite/SQLCipher。主要原因：

- **加密功能不能直接替換：**
  - 沒有從密碼推導金鑰（KDF），只吃原始金鑰，要自己做 KDF 和金鑰管理；
  - 沒有可用的 rekey；
  - 沒有 `sqlcipher_export`；
  - **`VACUUM INTO` 從加密資料庫輸出的檔案是明文**，搬家用的匯出包必須另寫。
- **讀不了現有的加密 archive：** 現有 SQLCipher archive Turso 打不開，所有加密用戶都要經過一次完整轉換。
- **Rust API 不能直接替換：** API 是 async 的，參數、行、錯誤和交易的型別都不同。`progress_handler` 在高階 API 上沒有開放，而匯出取消就靠它。
- **搜尋語意有缺口：** 單一詞的前綴搜尋（`42*`）在探測中只匹配到 `42` 本身。PathKeep 依賴前綴搜尋。
- **分組查詢沒有變快：** 6.4 秒對 6.8 秒。
- **原型裡觀察到建置後的行程卡住，原因未查明。**
- **讀取瀏覽器原始檔仍要用 SQLite：** 線上快照要走 SQLite 的 backup API，所以全換之後兩個引擎都會在執行檔裡。

成熟度按用戶要求不列入考量，以上都是功能和工作量的問題。

## 4. 選項

**A. 留在 FTS5，常見詞改成全局分段串流（Codex 正在做）**

- 符合 25,000 頁以下：照舊按相關度精確排序。
- 更多時：按時間由新到舊分段掃整個 archive。每次請求不超過 300 ms，計數按網址範圍累加到精確。
- 優點：完整覆蓋，沒有新依賴，能盡快取代違反規則的窗口。
- 缺點：常見詞不按相關度排。加密 archive 上，分組相關的工作依然慢。

**B. Tantivy sidecar 做排序與計數；SQLCipher 仍是 archive 的唯一真相**

- 常見詞也能在毫秒級按相關度排序，而且覆蓋全部結果。計數也是毫秒級。
- 要做的事：
  - 搜尋語意對齊：兩個 FTS 索引、中日韓、運算子、筆記和標籤；
  - 跨瀏覽器同網址合成一行，在 collector 裡按「第 k 個不同頁面」剪枝；
  - 篩選落在同一筆訪問；
  - 增量更新要有可重放的 outbox；
  - 撤銷匯入時不能洩漏；
  - 分頁游標釘住索引版本；
  - 首次建置要有預覽、進度，可以取消。
- **加密是最大的風險：** 要自己寫加密的寫入端、合併、崩潰恢復和換密鑰，這是安全代碼。研究提到另一條路，把 Tantivy 的區塊存進一個 SQLCipher 資料庫，重用現有的加密和交易機制，但還沒量。
- 依賴：Tantivy 有 16k 星、由 Quickwit 維護、MIT 授權，過門檻。

**C. Turso 只用來放搜尋索引（原生加密的 FTS）**

- 加密由引擎負責，不用自己寫 Directory。
- 但是：
  - 多一個資料庫引擎（約 +16 MB）；
  - 和加密 archive 之間不能 ATTACH，候選和補資料都要經過應用程式；
  - 前綴搜尋有缺口；
  - Tantivy 藏在 SQL 後面，**沒辦法用 B 需要的自訂 collector**（篩選推進、按頁面剪枝、時間決勝）；
  - 原型觀察到行程卡住。

**D. 整個資料庫換成 Turso** — 不建議，理由見第 3 節。

**E.（和上面都不衝突）現在就用 SQLCipher 加密 `derived/` 下的三個資料庫**

- 實測的「SQLCipher all」組合：在 1M 上，加密搜尋索引後，搜尋時間和現在差不多（56 ms 對 58 ms）。
- 這能補上 `WORK-ENCRYPT-AT-REST-ALL` 裡資料庫的部分。向量、抓取的內容、瀏覽器快照等不是資料庫的檔案，仍要另外決定。
- 要改的地方：`ATTACH … KEY ''` 的掛載方式、換密鑰流程、匯出時的暫存檔。

## 5. 建議

1. **A 先上。** 它把搜尋恢復成全局，取代違反規則的窗口，而且不論後面選什麼都需要：B 的研究也要求索引在建置或追趕期間，要有一個完整的備援搜尋。
2. **長期選 B，不選 C 或 D。** 決定因素是 B 能自訂 collector，而按頁面分組、篩選推進、時間決勝都需要它，C 做不到。加密先試「區塊存進 SQLCipher」這條路，避免自己寫密碼學；不行再做 AES-GCM Directory，並安排安全審查。
3. **E 盡快做**，和 A、B 獨立。這是現有引擎就能做的事，關掉一個已知的明文缺口。

B 開工前，需要先在 4 核 8 GB 的機器上，或用限制 CPU 和記憶體的方式，驗證建置時約 1 GB 的記憶體峰值和冷查詢的延遲。
